# LOLC URS .docx Formatting Spec
*Reverse-engineered at the raw XML level from four real LOLC files, cross-checked against each
other rather than trusted individually: Transaction Reversal – Interest Rollback URS V1.0, the
blank XX-Module and Master templates, and the Lending Module V0.1 draft. Facts below are only
kept where at least two of the four files agree; the previous version of this file was built from
a single sample no longer available for re-verification and, on cross-check, contained fabricated
table-color values. This is what STEP 3 in SKILL.md must apply exactly when generating the .docx.*

Read `/mnt/skills/public/docx/SKILL.md` before generating. The rules below are deliberately
specific — they were measured at the XML level, specifically to close the gap that caused past
output to drift in font, color, table style, and numbering from page to page. Treat every value
here as exact, not approximate.

### Why past output drifted (read this before writing the generation code)

The underlying LOLC template does **not** set Candara as the document's theme font. The theme's
major/minor font is Calibri. Every single heading and body run in the real samples carries an
**explicit** `Candara` font override at the run level, layered on top of styles that would
otherwise default to Calibri. The practical consequence: if you build the .docx by only setting
`docDefaults`/`styles.default.document.run.font` to Candara and rely on `HeadingLevel.HEADING_1`
etc. to inherit it, anything that doesn't get an explicit per-run font (stray paragraph marks,
table-of-contents entries, anything generated by a library's default heading style) will silently
render in Calibri instead, at the theme's default heading color rather than LOLC blue. This is
almost certainly the mechanism behind "some pages differ" — it's not random, it's specifically
whichever runs didn't get the explicit override.

**The fix:** when generating with docx-js, set Candara in `styles.default.document.run.font` AND
explicitly override the `Heading1`/`Heading2`/`Heading3` paragraphStyles with their own
`run: { font: "Candara", ... }` (see the Styles section of the docx skill for the override
pattern) AND make sure no TextRun anywhere omits a `font` property. Don't assume inheritance will
carry the font through every element type — verify it explicitly, especially in headers, footers,
table cells, and ToC entries.

**This same stripping mechanism is wider than just run-level fonts — confirmed to also strip
paragraph-level `w:tabs`/`w:ind` in at least one generation pipeline.** If the doc is generated,
then opened and saved via Word automation (COM) before being exported/finalized, that Save step
was confirmed (by inspecting `document.xml` before and after) to drop explicit `<w:tabs>` and
`<w:ind>` overrides from a paragraph's `pPr` — only `pStyle`, `numPr`, and `spacing` survived.
This is the identical class of defect as the font-stripping above (an explicit override silently
normalized away by a save round-trip), just hitting a different element. **This does not apply to
the normal generation path** (docx-js/python-docx writing the `.docx` directly, no COM step) — the
default numbering recipe below (`LevelSuffix.TAB` + real `indent: { left, hanging }`) matches all
three real sources exactly and should be used by default. Only if your specific pipeline confirms a
Word-automation save/round-trip step after numbering is applied, don't rely on `w:tabs`/`w:ind`
surviving it — see the "number-to-text gap" note in the numbering section below for the practical
consequence and the fallback fix (a literal space run instead of a tab-stop, accepted as a
narrower/uglier gap in exchange for surviving the Save).

## Spacing — full audit (headings, tables, captions, images, lists)

A user reported spacing problems beyond the front matter — inside tables and around image
captions specifically. Swept the whole document (not just the ToC region) for every spacing
transition that recurs enough to generalize. Two confidence levels below: **exact** (identical
across independent files, treat as a hard rule) and **bounded** (real samples vary, but never
exceed a stated limit — don't chase a single "correct" number that doesn't exist).

**Exact — style-level spacing values (`styles.xml`), apply as explicit per-run/per-paragraph
overrides, don't rely on inheritance:**

| Style | Spacing |
|---|---|
| `Heading1` | `before=240` (12pt), `after=0` |
| `Heading2` / `Heading3` | `before=40` (2pt), `after=0` |
| `Caption` | `after=200` (10pt), `line=240` `lineRule=auto` (exact single spacing) |
| `TableofFigures` (ToC/List of Figures/Tables entries) | `after=0` |
| `TOC1`/`TOC2`/`TOC3` (main ToC entries) | `after=100` (5pt) |
| Body paragraph (plain prose, e.g. Overview) | explicit **per-paragraph** `after=120` (6pt) — **not** inherited from `docDefaults`, which real files set to `after=200`/`line=276 auto` (Blacklist, Schedule Payment) or `after=160`/`line=259 auto` (Customer Occasion Alert — an older/different Word default template; **200/276 is the majority, 2 of 3 samples, and is what this skill's generator config below now targets**). If a generator lets body paragraphs fall back to the style/theme default instead of setting this explicitly, they'll render looser than the intended 6pt — same drift mechanism already documented for fonts, applied to spacing. |
| Multi-paragraph table cell content (e.g. story sub-points inside Action) | explicit `after=120`, `line=276` `lineRule=auto` (1.15 line spacing) — needed so consecutive points within the SAME cell have visible separation; omit this and back-to-back points in one cell run together with no gap. This is unrelated to the single-paragraph-cell / docDefault gotcha below — it's real per-paragraph content spacing, not a spacer relying on inheritance. |
| Single-paragraph table cell content (e.g. Document Information's "Drafted By" value) | **no override at all** — no `spacing`, no cell `margins`. Real files' own single-paragraph cells (confirmed: cover-page version table, Document Information, story-table row-label cells) carry no explicit `pPr` on the paragraph and no `tcMar` on the cell. **Do not add a per-cell `margins` override "for padding"** — a prior version of this skill's generator did (`margins:{top:80,bottom:80,left:100,right:100}` on every table-cell helper), which combined with the docDefault mistake below to inflate single-line row height to ~2.4x real (measured: real ≈14pt gap between single-line rows; the over-margined version produced ≈22-34pt). |

**CRITICAL — do NOT set a document-level default paragraph spacing (`styles.default.document.paragraph.spacing`) to match a real file's `docDefaults`.** An earlier version of this skill recommended exactly that (to fix the cover page's blank-spacer gap, see below) — it was wrong, confirmed via actual Word rendering with pixel-position measurement: setting `after=200/line=276 auto` at the document level cascades into every table cell that doesn't reference a named style with its own protective `pPr` (Document Information, Definitions & Acronyms, General Guide Line, story tables, Epic table, the cover table) and inflates single-line row height ~1.5-2.4x versus real files, depending on what else was also stacking with it. Table cells in real files carry no explicit `pPr` in the XML, but Word does **not** carry a paragraph's `after` spacing across a table row boundary the way it does between ordinary body paragraphs — leaving table-cell paragraphs with NO spacing override at all (docx-js's own internal per-paragraph default, effectively just single line-height) is what actually reproduces real row heights, confirmed to within 0.1pt (13.95pt generated vs 14.0pt real) once both the document-level default AND the per-cell `margins` override (row above) were removed.

**The correct, narrow fix for the cover page's blank-spacer gap is on `blank()` itself, not the
document default** — give `blank()` (and any other standalone body-level spacer/cover-page
paragraph that isn't inside a table: title, subtitles, the border-separator paragraph, the company
name/address block) its own explicit `spacing: { after: 200, line: 276, lineRule: "auto" }`. Since
`blank()` is never used as table-cell content, this cannot leak into any table, unlike the document-
level approach. Confirmed as a real, severe, multi-round defect via actual Word rendering: a
generated file's cover page had "LOLC Technologies" landing at ~51% down the page instead of the
real files' confirmed ~76-86%, because 9 stacked "empty" spacer paragraphs collapsed to near-zero
height instead of each carrying real files' ~22pt of inherited spacing — this was invisible to
every XML/count-based check this skill had (they check paragraph *counts*, never rendered height)
and took several rounds of user-reported "spacing still looks wrong" before being caught by
literally measuring rendered pixel positions against a real file — and the first fix attempt
(document-level default) then caused a second, different regression (table rows) that needed a
second measurement pass to catch and correct.

**A second, related gotcha this same default spacing surfaces: never end a section with a
standalone paragraph whose only content is a forced page break** (`new Paragraph({children:[new
PageBreak()]})`). Once that paragraph inherits the document default spacing (as above), it
produces a genuine extra **blank page** — confirmed twice this session, at two different section
boundaries, via real Word rendering (page-text extraction showing a lone space character occupying
an entire page). Setting `spacing:{after:0}` on that standalone paragraph is **not sufficient** —
it still carries the inherited `line=276 auto` line-height and the blank page persisted. The actual
fix: don't use a standalone page-break paragraph at all. Set `pageBreakBefore: true` directly on
the *next* section's own heading paragraph instead. This is what the real files effectively achieve
through natural page flow (their front matter is long enough to reach a new page on its own); a
short front matter needs the explicit `pageBreakBefore` property, never a dedicated break paragraph.

**Exact — adjacency, confirmed with zero gap paragraphs every time:**
- Heading immediately followed by its table (e.g. "Document Information" → its table): **0** empty paragraphs.
- Heading immediately followed by a table's caption, caption immediately followed by the table itself (e.g. "Data Dictionary" → "Table 1 - Data Dictionary" caption → the table): **0** empty paragraphs at either transition.
- An embedded image immediately followed by its caption below it: **0** empty paragraphs.
- One figure's caption immediately followed by the next figure's image (consecutive screenshots in Diagrams and Examples): **0** empty paragraphs — don't insert a blank line "to separate" consecutive figures; the Caption style's own `after=200` spacing is the entire visual gap.
- No trailing empty paragraph after the last content paragraph *inside* a table cell, even a multi-point one (confirmed: a 7-point Action cell ends cleanly on its 7th paragraph, no 8th empty one).

**Standardized (real samples vary 0-or-1; generation always uses 1):** after a table or a bullet
list (Assumptions/Risks/Scope/Test Scenarios), insert **exactly 1** empty paragraph before the
*next* heading. Real samples show both 0 and 1 at different transitions within the same document
(0 after General Guide Line's table before "Open Questions"; 1 after Scope's bullets before
"Epic: Narrative and Statement") — since neither is more authoritative than the other, generation
picks one value and applies it consistently everywhere this transition occurs, rather than
reproducing the real documents' own inconsistency. Everywhere else (heading→table, heading→
caption→table, image→caption, caption→next image — the "Exact" list above), the rule stays 0,
unchanged. **2 or more stacked empty paragraphs anywhere in Section 1 onward (the body content
flow) is never acceptable.** Don't manually pad spacing between sections "for readability" beyond
this one paragraph — the heading styles' own `before` spacing is sized to do the rest of that job.

**Cover page is a documented exception to the above, confirmed against a real reference file
(`Blacklist_Rule_to_Transaction_Event_Mapping_V0.1.docx`, body children 0-25):** the cover page
uses stacked empty paragraphs as its vertical-layout mechanism, not `spacing.before` on the
following paragraph. Confirmed shape: **3** empty paragraphs before the title (pushes the title
block down the page), **1** empty paragraph between the subtitle and the version/date table, **9**
empty paragraphs between the table and the next element, then a border-only paragraph (bottom
border only, no text — a visual rule, not a spacing paragraph) immediately before the "LOLC
Technologies" company-name paragraph. This is a distinct mechanism from body-flow section-transition
spacing and must not be "fixed" to 0-or-1 by a generator or a check script — `check_body_spacing()`
must only scan from the first Section-1 heading onward, not the cover page / front matter.

**These 9 (and 3, and 1) empty paragraphs only produce the correct visual gap if each one carries
its own explicit `spacing: { after: 200, line: 276, lineRule: "auto" }` — see the CRITICAL gotcha
in the Spacing section above for why this must be set per-paragraph on `blank()` and NOT as a
document-level default.** Getting the paragraph *count* right (9) is necessary but not sufficient:
each of those paragraphs is bare in the real file (no `pPr`), so matching that literally (a bare
`Paragraph({})`) renders at near-zero height instead of real files' ~22pt each. Confirmed: 9
correctly-counted but unstyled empty paragraphs landed "LOLC Technologies" at roughly the middle of
the page instead of near the bottom.

### Table styles — two real mechanisms, used for different tables; know which applies where

**Correction to a correction:** the first hardening pass on this skill concluded `D5DCE4` was
fabricated and should never be used. That was wrong, caught on a second, deeper XML pass — `w:shd`
cell-level inspection (not just `tblStyle` names) shows `D5DCE4` genuinely appears, repeatedly and
consistently, in real signed and drafted LOLC files. It just isn't a table **style** — it's a
manual per-cell shading override on specific cells in tables that otherwise carry no built-in
style fill. Two independent real mechanisms coexist in the same documents:

**Mechanism 1 — named Word table style (`tblStyle`), no manual shading needed:**

| Style ID | Look | Used for |
|---|---|---|
| `GridTable4-Accent3` | Header row white bold text on dark grey `A5A5A5` fill (theme `accent3`); `C9C9C9` borders; body bands white/`EDEDED` — all from the style's own `tblStylePr type="firstRow"`/`band1Horz`, confirmed via direct XML inspection: the header cells in the V1.0 sample carry **no** `w:shd`, **no** `w:b`, and **no** `tblBorders` at all in their own `tblPr` — everything renders purely from the named style | **Data Dictionary and E2E Impact Identification only** are actually `GridTable4-Accent3` in the V1.0 sample (`Customer_Occasion_Alert_Configuration_SMS_Email_V1.0.docx`) — corrected; an earlier version of this table wrongly claimed Revision History and Open Questions are too. In that same sample those two are `PlainTable1`. This skill still deliberately generates all four with `GridTable4-Accent3` for consistency (single mechanism, immune to per-cell drift) — that is a generation-policy choice, not a claim every real sample does it this way; two of three locally available real files use plain `TableGrid` with no header color at all for all four of these tables. |
| `PlainTable1` | No header fill at all, bold text only; thin `BFBFBF` borders; body bands white/`F2F2F2` | Seen in some samples (Customer Occasion Alert) for Revision History/Open Questions specifically — **not** the base style this skill targets for Definitions & Acronyms or story tables; see the corrected `TableGrid` guidance below, confirmed against the file most actively compared against (Blacklist). |

**Mechanism 2 — `PlainTable1` or `TableGrid` base style PLUS a manual `w:shd fill="D5DCE4"` on
specific cells:**

| Table | What gets `D5DCE4` | Confirmed in |
|---|---|---|
| Cover-page version table | The label column only (Document Version / Release Date / Number of Pages) — value column has no fill | Lending V0.1 — **base style is named `TableGrid`, not `PlainTable1`** (corrected; confirmed via direct `tblPr`/`tblStyle` inspection, contradicting an earlier, wrong version of this table). The table is also `jc="center"` (both `tblPr` and each `trPr`) and full content width — `tblW w="0" type="auto"` with `gridCol` widths 4513/4513 (9026 DXA total at 1" margins), not a narrower left-aligned table. |
| Document Information (1.1) | The label column only (Drafted By / Reviewed By / ...) | **Both** Lending V0.1 and Transaction Reversal V1.0 — the one table where this is universal regardless of document maturity |
| General Guide Line (1.6) | The full header row (Category / Guideline-Comment / Applicability-Notes), on top of base style `TableGrid` | Lending V0.1 |
| Epic table (Section 6) | The merged title row only (e.g. "Lending Module", `gridSpan` across both columns, bold) — the Who/Needs/Product/ROI rows below have no fill | Lending V0.1 |

**Which mechanism to use when generating:** apply Mechanism 1 (named `GridTable4-Accent3` style)
to Revision History, Open Questions, Data Dictionary, and E2E Impact Identification — it's a
single style reference, immune to the per-cell drift that caused past problems, and matches the
most mature real sample. Apply Mechanism 2 (`D5DCE4` manual shading on label/header cells only) to
the cover-page version table, Document Information, General Guide Line, and the Epic table's
merged title row. **Base style is `TableGrid` for every one of these, and for every OTHER table
too (Definitions & Acronyms, story tables) — not `PlainTable1`.** Corrected: an earlier version of
this row said `PlainTable1` for everything except the cover table specifically, based on a
different, less-authoritative sample; re-checked directly against `tblPr/tblStyle` in
`Blacklist_Rule_to_Transaction_Event_Mapping_V0.1.docx` — the file this skill's output is most
often actively compared against — and every single body table in it (Document Information,
Definitions & Acronyms, General Guide Line, story tables, Epic table, cover table) uses
`TableGrid`. **Every one of these tables must set `style: "TableGrid"` explicitly when
generating** — omitting the style reference entirely (relying only on manual `tblBorders`, which
several rounds of this skill's own generated output did) still renders visible borders correctly,
but silently loses `TableGrid`'s own default cell margins, making numbered content inside those
cells (row-content numbers like "7.1.1.1.") sit flush against the cell's left border instead of
with real files' visible padding — confirmed via direct user-provided screenshot comparison, not
caught by any structural check since borders/shading/content were all otherwise correct.

**Never do either of these:** don't apply `D5DCE4` as a full table style (it's cell-level, not a
`tblStyle`), and don't apply it to body/value cells — only label or header cells get it. Both
were real mistakes in earlier passes on this skill.

**Divider/title rows inside a table:** the Epic table's module-name title row is merged across
every column (`gridSpan` = column count), bold, and shaded `D5DCE4`. The target 8-column Data
Dictionary format does **not** use divider rows — group by repeating the Feature value in each
row instead (confirmed from the V1.0 sample). A merged, bold, unshaded divider-row-per-story
pattern does appear in Data Dictionary in one V0.1 draft, but that draft also used a simpler,
non-standard 4-column table overall — treat the divider row as part of that same draft-stage
shortcut, not a pattern to combine with the target 8-column format.

- E2E Impact Identification Table header is centered (the only table where header text is
  centered rather than left-aligned) — this is real and deliberate, keep it.
- **Cell margins: none set explicitly anywhere** (no `tcMar` on any cell, no `tblCellMar` on any
  table's own `tblPr`, in any real file checked). Do not set `margins` on any `TableCell` in this
  document — but see the next section: "none set explicitly" does NOT mean "no injection needed."
  Real cell padding is real and visible (5.4pt/108 twips, confirmed by direct Word-COM
  `Cell.LeftPadding` measurement) — it comes entirely from style inheritance, and that inheritance
  silently fails to resolve at all unless the styles it depends on are explicitly present in
  `styles.xml`, not just referenced by name.

### Real cell padding requires injecting `TableNormal` (and, for `GridTable4-Accent3`, an explicit `tblCellMar` too) — `check_no_cell_margins()` cannot catch this

**A user reported cell padding wasn't actually visible despite `check_no_cell_margins()` passing —
correct on both counts.** That check only confirms no *explicit* `tcMar`/`tblCellMar` override
exists anywhere; it cannot detect that the *implicit* default margin isn't being inherited at all,
which is a completely different, invisible-to-XML-structure failure mode. Confirmed via direct
Word-COM `Cell.LeftPadding`/`RightPadding` queries (not PDF text-position inference, which turned
out unreliable — see below) on both a generated file and a real reference file:

| | Real file | Generated file (before fix) |
|---|---|---|
| `TableGrid`-styled cell | 5.4pt | 0pt |
| `GridTable4-Accent3`-styled cell | 5.4pt | 0pt |

**Root cause, `TableGrid`:** real cell padding does not come from `TableGrid` itself — every real
file's own `TableGrid` style definition has no `tcMar`/`tblCellMar` of its own. It comes from
**`TableNormal`**, the actual foundational `w:default="1"` table style everything else is
`w:basedOn`, via *its* `tblCellMar` (top=0, left=108, bottom=0, right=108 twips — 108 twips =
5.4pt, exactly matching the measurement). This generator had **no `TableNormal` definition at all**
— not just no `TableGrid` definition — so there was nothing for any table style to inherit padding
from, regardless of which named style was referenced. Fix: inject both `TableGrid`'s own definition
(verbatim, borders only) **and** `TableNormal`'s definition (verbatim, the `tblCellMar` shown above)
into `styles.xml`. `TableGrid` alone was tested first and confirmed insufficient on its own — adding
just `TableGrid` still measured 0pt; only adding `TableNormal` as well fixed it. This also fixes
every other table style that's `basedOn="TableNormal"`, not just `TableGrid`.

**`GridTable4-Accent3` needed one more fix beyond this**, confirmed by testing in isolation: even
with `TableNormal` correctly injected, and with `GridTable4-Accent3`'s own style definition
byte-for-byte identical to a real file's (confirmed by direct diff, including real
`w:themeColor`/`w:themeFill` attributes and a real `word/theme/theme1.xml` part — docx-js emits
neither by default, which is *also* the cause of a separate, previously-patched-around defect where
`GridTable4-Accent3`'s header fill rendered bright green instead of grey, since with no theme part
Word substitutes its own built-in default Office theme where `accent3` is green), a table styled
`Grid Table 4 - Accent 3` **via Word's own COM object model** (not this generator's XML at all —
ruling out any generation-specific cause) still measured 0pt padding in this document, while the
identical style correctly resolves 5.4pt in a real file. Ruled out, confirmed to make no difference
in isolation, before finding the actual fix: a missing `<w:pPr>` element in the style (added — no
effect, `GridTable4-Accent3` already had this one; it was `TableGrid`'s missing element, a
byte-level diff finding, not a guess), the `tblLook` element's legacy `w:val` hex bitmask (real
files have `w:val="04A0"` alongside the newer boolean attributes; docx-js emits only the booleans —
added, no effect on padding, though still worth fixing on its own merits since every real file has
it), `w:cnfStyle` conditional-formatting-region markers on the header row/cells (real files have
these; docx-js has no API for them — added by hand, no effect). **What actually works: an explicit
`<w:tblCellMar>` directly on `GridTable4-Accent3`'s own `tblPr`**, not relying on the
`basedOn="TableNormal"` inheritance chain at all — confirmed by direct before/after
`Cell.LeftPadding` re-measurement. The underlying mechanism is not fully understood (Word's built-in
"Grid Table" style family appears not to reliably inherit `tblCellMar` through `basedOn` the way
"Table Grid" does, even with otherwise-identical definitions) — treat this as a confirmed, working
fix, not a fully explained one. Don't remove the explicit `tblCellMar` as "redundant with
TableNormal" without re-testing with an actual `Cell.LeftPadding` COM query — visual inspection and
every XML-structural check (including `check_no_cell_margins()`) are blind to this specific defect
class.

**Methodology note:** the first attempt at measuring this used PDF text-position inference (Word-COM
export to PDF, then comparing a text run's left edge against a nearby vector-drawn border line via
PyMuPDF). That approach produced a confusing false lead — it happened to compare two structurally
different tables (different column counts/widths, different `jc` centering) between the generated
and real files, since both happened to contain matching cell text ("Drafted By") in different
contexts. Querying Word's own resolved `Cell.LeftPadding`/`RightPadding` properties directly via COM
is unambiguous and immune to this — prefer it over PDF-position inference for any cell-padding/
margin question.

### Numbering — heading indent must increase progressively per level, not just the text after it

A prior version of this skill's numbering config set `hanging` equal to `left` at every level
(e.g. level 0 `left:360,hanging:360`, level 1 `left:504,hanging:504`, ...). This is wrong: since a
level's number-glyph start position is `left - hanging`, setting them equal makes that position 0
at **every** level — "1." and "1.1." both begin flush at the same left position, only the tab
distance to the following text differs. Confirmed wrong via a direct user-provided screenshot
comparison ("1." flush left, "1.1." not visibly indented from it) against the real file, where the
number glyph itself is progressively indented per level. Real values, read directly from
`Blacklist_Rule_to_Transaction_Event_Mapping_V0.1.docx`'s own `numbering.xml` for its Document
Control heading list:

| Level | `left` | `hanging` | Number starts at |
|---|---|---|---|
| 0 (h1, e.g. "1.") | 720 | 504 | 216 |
| 1 (h2, e.g. "1.1.") | 1080 | 504 | 576 |
| 2 (e.g. "1.1.1.", rarely used) | 1440 | 360 | 1080 |

This applies to **heading levels only** (h1/h2, and the equivalent h1Second/h2Second second-list
levels — same values, confirmed identical for the Data Dictionary heading's own numId). Deeper
levels used for **table-cell content** (story-table row labels like "7.1.1.", and numbered
sub-points like "7.1.1.1.") are a *different, separate* real numbering list in the reference file
and genuinely do use `left == hanging` (720/720 and 900/900 respectively — number flush at 0
relative to the cell's own content area) — do not "fix" those to match the heading progression;
`check_numbering_gap()`'s own documentation already established this as intentional. The visible
gap between "7.1.1.1." and the cell's left border in a real file comes from the table's own
`TableGrid` cell margin (see Table styles above), not from the numbering indent — getting the
numbering indent right without also setting `style: "TableGrid"` on the table still renders numbers

### Column widths — the most common cause of bad-looking tables

Several tables in this format are wide (5–8 columns) and will wrap into an unreadable vertical
ladder of single words if columns are sized evenly or too narrow. Use these proportions (content
width ≈ 9000 DXA at 1" margins on US Letter; scale proportionally for other page widths):

| Table | Column proportions (left → right) |
|---|---|
| Data Dictionary (8 cols) | Feature 10.8% · Field Name 11.7% · Data Type 11% · Source/Retrieve From 10.4% · Constraint/Description 16.7% · Sample Data 15.1% · Data Validation 13.8% · Max Length 10.4% — corrected; an earlier version of this row (12/12/10/12/28/10/12/4%) was never actually cross-checked against a real file's own `gridCol` values. The old 4% Max Length column, combined with generated content like "Per template" (longer than the terse values real samples use there), rendered as one character per line — confirmed by actually rendering the generated file, not visible from XML alone. Widths here are read directly from `Customer_Occasion_Alert_Configuration_SMS_Email_V1.0.docx`'s own `tblGrid` (977/1060/989/938/1504/1365/1245/938 of 9016 total). |
| E2E Impact Identification (3 cols) | Area 20% · What to Capture 30% · Impact Description 50% |
| Story tables (2 cols) | Row label 20% · Content 80% |
| Open Questions (5 cols) | # 5% · Date 12% · Question 48% · Owner 15% · Status 20% |
| Document Information / Revision History / General Guide Line | Give the description/comment column at least 45% of total width; never let a header word (e.g. "Status", "Description") be narrower than the word itself needs at 11pt — if a single header word is wrapping onto two lines, the column is too narrow |

The rule of thumb: before finalizing column widths, check whether any column header word is
longer than the column is wide. If "Status" or "Description" would need to wrap, widen that
column and narrow a less text-heavy neighbor instead.

### Table of Content / List of Figures / List of Tables must be genuine, live, updatable Word fields — read before touching any of this again

**Explicit, repeated user requirement: the ToC/LoF/LoT must behave exactly like a TOC someone
inserted themselves in Word** — right-click → Update Field (or F9) recomputes it correctly after
the document is edited later, and Word's field shading shows the entries as real field content, not
typed text. An earlier version of this section documented stripping the field down to static
text (matching what two real, already-approved LOLC reference files happen to contain, since both
had already been through a real one-time Word update-and-save cycle by a human at some point). That
approach was explicitly rejected — a stripped/static ToC can never auto-update again after editing,
which is not what "generated, not typed" means to the person using this document day to day. Do not
reintroduce field-stripping; the correct fix keeps the field genuinely live.

**The dialogs this was chasing** ("may refer to other files" on open; "Update Table of Contents —
entire table / page numbers only" on update) **turned out to have nothing to do with whether the
field is live** — a completely native Word-built TOC field (created directly via Word COM, no
docx-js, no postprocessing at all) is just as "live" as anything this generator produces, and real
Word documents with live TOC fields do not show a stray dialog on every normal reopen once they've
been through one real save. The actual causes, both fixable while keeping the field live:

1. **docx-js wraps `TableOfContents()` output in a `<w:sdt>` content control.** A native Word TOC
   field has no such wrapper (confirmed directly: built one via Word COM, inspected its XML — zero
   `<w:sdt>`). Strip only the `<w:sdt><w:sdtPr><w:alias .../></w:sdtPr><w:sdtContent>` /
   `</w:sdtContent></w:sdt>` tags; the actual field underneath (`begin`/`instrText`/`separate`/
   `...cache.../end`) stays completely intact.
2. **The field's `begin` fldChar carries `w:dirty="true"`**, which is the correct signal only while
   the cache is genuinely empty/stale (a field that still needs computing). Once the cache holds
   real, correct content — see below — this flag is simply wrong, and is what makes Word think an
   update is needed on every open. Clear it once the content it would flag as stale is no longer
   stale. (Do **not** clear `dirty` while the cache is still a placeholder — tried once already,
   combined with an empty cache it broke auto-population entirely. Order matters: fill the cache for
   real first, only then clear `dirty`.)

**Filling the cache with real content, all in `postprocess.py` (not `generate.js`/`main.js`/
`content*.js`):**

1. Reads `numbering.xml` to resolve each heading's real section number (per-`numId` counters seeded
   from each level's own `w:start` value), walks every paragraph to bookmark each `Heading1`/
   `Heading2` and every Figure/Table caption (matched by the same `44546A` italic-color + text-prefix
   pattern `figureCaption()`/`tableCaption()` emit) with a sequential `_TocN` name, and builds one
   real `TOC1`/`TOC2`/`TableofFigures`-styled hyperlink+`PAGEREF` paragraph per entry
   (`entry_paragraph()`). Verified directly against Word's own `ListFormat.ListString` computation
   on the body headings — every cached ToC number matches the real body section number exactly,
   including the real template's own intentional duplicate "7." on both Features/Stories and Data
   Dictionary. Every text run this generates needs explicit `w:ascii="Candara" w:hAnsi="Candara"` on
   its `rFonts` (not just `w:cs`, which satisfies real files' own cache but not this skill's stricter
   `check_fonts()`).
2. **Real page numbers cannot be computed by this pipeline at all** — pagination depends on an
   actual layout engine, which only Word has. `postprocess.py` alone can only fill the cache with a
   placeholder. This is a required, separate second phase, not optional polish: after
   `node main.js && python postprocess.py` produces the file, run Word-COM read-only —
   `doc.Repaginate(); doc.Fields.Update()`, then read each `PAGEREF` field's `.Result.Text` (filter
   `Field.Type -eq 37`) — to get real per-bookmark page numbers, close **without saving**
   (`doc.Close($false)`, never `doc.Save()` — see the Word-COM destructive-save warning elsewhere in
   this file), then run `patch_page_numbers.py <docx> <mapping>` to substitute the real values into
   the already-generated file's cache in place. Confirmed safe: the docx passes all 13 checks
   identically before and after this read-only COM pass.
3. Strip the `<w:sdt>` wrapper (point 1 above) and clear `dirty` (point 2 above). One more thing
   falls out of doing this on docx-js's actual output shape: docx-js puts the field's own
   `begin`/`instrText`/`separate` in a bare paragraph before the first entry, and its lone `end` in
   another bare paragraph after the last entry — both real paragraphs with no `<w:t>`, so Word
   renders each as a genuine extra blank line, and (checked against a native Word TOC field, which
   folds its begin/end into whatever adjacent paragraph is structurally convenient rather than using
   a dedicated blank one) there's no requirement to keep them standalone. Fold the begin/instrText/
   separate runs into the **first** entry paragraph and the end run into the **last** entry
   paragraph — same pattern already used for each entry's own nested `PAGEREF` field, which already
   coexists with visible text in one paragraph.

**Verification performed, in order:**
- All 13 mechanical checks pass, including `check_front_matter`'s spacer-paragraph counting (this
  specifically catches a regression if the begin/end merge above is skipped or done wrong — the
  bare boundary paragraphs get miscounted as spacer blanks otherwise).
- Zip integrity and every XML part parses clean.
- Direct XML inspection: `<w:sdt>` count 0, `w:dirty` count 0, 29 bookmarks present and referenced.
- Opened the file the way the user actually opens it (`Start-Process` on the `.docx`, not COM
  automation) and screenshotted: no dialog, correct real entries, correct real page numbers.
- Right-clicked inside the ToC: context menu shows **Update Field** / **Edit Field** — confirmed

- Every visual check was done via a real, visible Word window opened the same way the user opens

## Numbering is one continuous system, not several separate features

Everything in a real LOLC URS that looks like a number — section headings (`1.`, `1.1.`),
Assumption/Risk/Scope bullets (`1.4.1.`, `1.4.2.`), and story sub-points (`7.1.2.1.`) — is driven
by the **same mechanism**: a real Word multilevel decimal list (`w:numPr`, `ilvl` = depth),
applied to a paragraph. Treat "apply real list numbering, not typed text" as the one rule behind
every numbering-looking element in the *document body*, not a story-specific fix. There is exactly
**one** legitimate exception to this rule, and it is not the row-label prefix (an earlier version
of this section wrongly said "User & Function" was exempt — it is not; `check_numbering()` requires
real `numPr` on all 6 story row labels with no exception, confirmed achievable against the Master
Template):

**The exception is Table of Content / List of Figures / List of Tables entry text.** A real Word
TOC-type field's cached entries are a flat text *copy* of whatever the source heading rendered as
at last update — including its number — not a live reference to the heading's own `numPr`. This is
inherent to how any real Word TOC field caches results, confirmed directly against
`Blacklist_Rule_to_Transaction_Event_Mapping_V0.1.docx`'s own `document.xml`: its "1. Document
Control", "1.1. Document Information", etc. TOC entries all carry the number as ordinary `<w:t>`
text, same as this generator's `entry_paragraph()` output (see the "may refer to other files"
section above). This is real, confirmed-correct behavior, not a defect — `check_numbering()`
deliberately excludes any text inside a `<w:hyperlink w:anchor="_Toc...">` span for exactly this
reason. If a typed number is spotted inside the ToC/LoF/LoT front-matter pages specifically, that is
expected and matches real files; a typed number anywhere else in the document body is a real defect.

- Section headings: `ilvl=0` → `1.`, `ilvl=1` → `1.1.`
- Story sub-points inside Action/Result/etc.: `ilvl=3` on a **second**, independent multilevel
  list (see below).
- **Assumptions (1.4), Risks (1.5), Scope in/out (5.1/5.2), Test Scenarios — confirmed as a plain
  bullet list** (`numFmt="bullet"`, Wingdings `•`, `ilvl=0` on their own list, independent of the
  heading numbering), consistently across all four sections in the V1.0 sample. This is real list
  formatting (`w:numPr`), not typed dash characters, but it is a bullet, not a number — don't
  apply decimal sub-numbering here. (One real V0.1 draft used decimal sub-numbers, e.g. `1.4.1.`,
  for its Assumptions/Risks specifically — treat that as draft-stage inconsistency, not the
  target; the V1.0 sample's uniform plain-bullet treatment across all four sections is the more
  authoritative, internally-consistent convention.)

## Numbered sub-points inside story cells — use a real Word multilevel list, not typed digits

**This is the fix for "auto numbering defects, indentation" complaints** — verified directly
against the Action cell of a real signed-off story (Transaction Reversal V1.0, Story 03): the
individual points inside a story's Action/Result/Pre-Conditions/Trigger cell (the ones that render
as `7.3.2.1.`, `7.3.2.2.` ...) are **separate paragraphs, each carrying real `w:numPr` list
numbering** (`ilvl` 3, a decimal multilevel list with `lvlText` `%1.%2.%3.%4.` and a matching
hanging indent), not one paragraph with the digits typed into the text. Word generates the visible
number from the list definition; it is not present as literal text in the file at all.

**Why this matters for generation:** if you type `"7.3.2.1.  System shall..."` as literal text
instead of applying real list numbering, you get **exactly the symptoms confirmed by testing real
generated output**: the digits are plain editable text (select them, they behave like any other
word — because they are), the indentation doesn't match Word's own hanging-indent math for that
level, and the numbers don't renumber when a point is added/removed/reordered — because there is
no field there for Word to recalculate, just a string that happens to look like one.

**The fix — concrete, not descriptive. Use this exact pattern (docx-js). The mechanism (`suffix:
LevelSuffix.TAB` + the level's own `indent: { left, hanging }`, no paragraph-level `w:ind`/`w:tabs`
override, no `w:suff` element) matches all three real sources at the raw XML level. The specific
indent widths below are wider than what was originally measured off Transaction Reversal V1.0
(which had 648-720 twips at its deepest level) — confirmed on a real generated file that 648 twips
is not reliably enough headroom for a full 4-segment number like `7.2.2.11.` at 11pt Candara: the
number's own rendered width sometimes leaves no room for the tab to land at the intended hanging
stop, so Word falls back to its generic default tab stops instead — producing a visibly wider,
inconsistent gap on some sibling numbered paragraphs but not others (same number of digits, same
level, same everything else), and misaligned wrap lines (the first line's text gets pushed out by
the tab overflow while the paragraph's true `left` indent, which continuation lines wrap to, stays
at the un-overflowed value). The widths below give real headroom at every level so this can't
happen — treat 648-style "just barely fits" values as a defect, not a valid alternative:**

```js
const { Document, Paragraph, TextRun, AlignmentType, LevelFormat, LevelSuffix } = require("docx");

const doc = new Document({
  numbering: {
    config: [
      {
        // One list per numbering "chain" — headings 1./1.1./1.1.1. is a separate chain
        // from story sub-points 7.1.2.1., which is separate again from the Data-Dictionary-
        // onward restart chain. Do not reuse one reference for unrelated numbering.
        reference: "story-subpoints",
        levels: [
          { level: 0, format: LevelFormat.DECIMAL, text: "%1.", alignment: AlignmentType.START,
            suffix: LevelSuffix.TAB,  // matches real samples: number, then a tab to the hanging-indent stop
            style: { paragraph: { indent: { left: 360, hanging: 360 } }, run: { font: "Candara" } } },
          { level: 1, format: LevelFormat.DECIMAL, text: "%1.%2.", alignment: AlignmentType.START,
            suffix: LevelSuffix.TAB,
            style: { paragraph: { indent: { left: 504, hanging: 504 } }, run: { font: "Candara" } } },
          { level: 2, format: LevelFormat.DECIMAL, text: "%1.%2.%3.", alignment: AlignmentType.START,
            suffix: LevelSuffix.TAB,
            style: { paragraph: { indent: { left: 720, hanging: 720 } }, run: { font: "Candara" } } },
          { level: 3, format: LevelFormat.DECIMAL, text: "%1.%2.%3.%4.", alignment: AlignmentType.START,
            suffix: LevelSuffix.TAB,
            style: { paragraph: { indent: { left: 900, hanging: 900 } }, run: { font: "Candara" } } },
        ],
      },
    ],
  },
  sections: [ /* ... */ ],
});

// Applying it to an Action-cell sub-point:
new Paragraph({
  numbering: { reference: "story-subpoints", level: 3 },   // <-- this makes the number real
  children: [
    new TextRun({ text: "System shall evaluate the reversed transaction group..." }),
  ],
});
```

**Do not add a literal space/tab character as the first run of the text.** The gap comes entirely
from `suffix: LevelSuffix.TAB` plus the level's own `indent: { left, hanging }` — that combination
is what makes Word jump straight to the hanging-indent stop after the number (a wide, consistent
gap, and correct wrap-alignment for continuation lines) instead of a cramped, font-width gap. A
paragraph that starts its text with `"  System shall..."` renders a *narrower and less consistent*
gap than the real samples, not a safer one — this was corrected after checking the actual pipeline
that motivated the earlier `LevelSuffix.NOTHING` + literal-space-run advice (see below); that
advice does not match what real signed-off documents contain and should not be the default.

**This is a general rule, not a story-subpoints-only fix — apply the same headroom principle to
every decimal-numbered list in the document, including the separate heading chain (`1.`, `1.1.`,
`1.2.` ... up to whatever the document's actual highest section/subsection number is).** Confirmed
on a real file across three separate list levels in the same document, not just one: the top-level
heading list (`ilvl=0`, tight at 360-twip hang-back — fine for `1.`-`9.`, overflowed at `10.`/`11.`
onto a default tab stop), the sub-heading list (`ilvl=1`, tight at 360 — `1.2.` and `1.3.` rendered
with zero gap while `1.4.` at the identical width happened to render correctly, because a
near-the-edge hang-back doesn't fail *every* instance uniformly, it fails unpredictably depending
on sub-pixel font-metric rounding), and the story-subpoint content level (`ilvl=3`, tight at 648).
All three were the same root cause at different levels. **When sizing any level's `hanging` value,
size it for the widest number that level will ever need to render in this document (check how high
the actual section/story/row count goes), not for the narrowest case that happens to fit during a
quick check** — a hang-back that "looks fine" on `1.` or `7.1.1.` and is only tested on single-digit
examples will not reliably survive reaching double digits. As a floor: 1-segment numbers need at
least 504 twips of hang-back, 2-segment at least 504, 3-segment at least 720, 4-segment at least
900 — these are the values used above and confirmed sufficient; do not go narrower without
re-verifying against the document's actual highest numbers at each level.

**Two gaps closed after another session flagged them, both confirmed for real by re-checking
`numbering.xml` (not document.xml) directly:**

- **The number glyph has its own, third font source — `style: { run: { font: "Candara" } }` on
  each level above, not just the paragraph/run font.** The rendered number (e.g. "7.1.2.") is not
  a `<w:t>` run in `document.xml` at all — it's synthesized by Word from the list level's own
  `<w:lvl><w:rPr><w:rFonts>` in `numbering.xml`. A document can have every single text run
  correctly set to Candara and still render every number in theme Calibri, because that's a
  separate font declaration entirely. Confirmed via direct inspection: even the V1.0 reference
  file has this gap at multiple levels of its own main heading list (only some levels carry an
  explicit override, most don't) — this is a real, previously invisible defect class, not
  theoretical. `check_fonts()` below has a second pass specifically for this.
- **`suffix: LevelSuffix.TAB` + the level's own `indent: { left, hanging }` is the default, and
  matches all three real sources exactly — use it unless the specific condition below applies.**
  An earlier pass of this file swapped the default to `LevelSuffix.NOTHING` + a literal 2-space
  run, reasoning that a Word-automation save/round-trip step strips paragraph-level `<w:tabs>`/
  `<w:ind>` the same way it strips run-level fonts, leaving a bare tab that snaps to Word's generic
  default tab stops and renders inconsistently between sibling numbered items. That reasoning is
  real, but it's a description of one specific broken pipeline (something in the generation chain
  re-opens the file in a live Word instance and calls `.Save()`), not the general case — and it was
  wrongly applied as the default for every pipeline, including the normal case where `docx-js` or
  `python-docx` writes the `.docx` directly with no COM-automation step in between. In the normal
  case, the space-run version is strictly worse: it produces a narrow, font-width gap instead of
  the wide, hanging-indent-aligned gap the real samples have, and it does not reliably reproduce
  Word's wrap-alignment for continuation lines the way a real `ind: { hanging }` does.

  **Use `LevelSuffix.TAB` (the default recipe above) unless you have confirmed, for this specific
  generation pipeline, that a Word-COM-automation Save step runs after the numbering is applied and
  strips `w:ind`/`w:tabs`.** Only in that confirmed case, fall back to the space-run workaround:
  ```js
  new Paragraph({
    numbering: { reference: "story-subpoints", level: 3 },
    children: [
      new TextRun({ text: "  ", font: "Candara" }),  // literal 2-space gap — survives Save, tab-stops don't
      new TextRun({ text: "System shall evaluate the reversed transaction group..." }),
    ],
  });
  ```
  This is a narrower, uglier gap than the real default — accept it only as a defensive measure
  against a specific pipeline defect, not as a general improvement. If unsure which pipeline is in
  use, generate with the default `LevelSuffix.TAB` recipe and check the actual output (Pass 2 of
  the validation gate) before assuming the fallback is needed.

The `numbering: { reference, level }` property on the `Paragraph` is what makes the number a real,
Word-native, editable/renumbering field. **If a `Paragraph`/`TextRun` anywhere contains the digits
themselves as string content (e.g. `text: "7.1.2.1.  System shall..."`), that paragraph is broken
regardless of how correct the digits look when first generated.** Bullets (Assumptions, Risks,
Scope, Test Scenarios) use the same mechanism with `format: LevelFormat.BULLET, text: "•"` instead
of decimal — still `numbering: { reference, level }` on the paragraph, never a typed `•` or `-`
character in the text, and the same `suffix: LevelSuffix.NOTHING` + literal-space-run fix above
applies to the gap between the bullet glyph and the text, for the same reason.

**If generating with python-docx instead of docx-js:** python-docx's high-level API does not
expose multilevel list numbering at all — `document.add_paragraph(style='List Number')` only
gives single-level numbering and still risks the same failure for anything past level 0. Real
multilevel numbering requires direct `numbering.xml` part manipulation via `docx.oxml` (define the
`abstractNum`/`num` elements yourself, same shape as the XML this file was reverse-engineered
from, then set `w:numPr` on each paragraph's `pPr` via `oxml`). If you can't implement that
reliably, say so to the user explicitly rather than silently falling back to typed digits.

**Patching an already-generated real `.docx` in place is a different, riskier operation than
building one fresh — do not reserialize the whole `document.xml`/`numbering.xml` tree to make a
small fix.** Confirmed on a real file: reading a part with `xml.etree.ElementTree.fromstring()`,
editing a few attributes, and writing it back with `ET.tostring()` produced XML that was still
well-formed (passed `ET.fromstring()` again, passed a zip-integrity check) but that Word refused to
open — "Word found unreadable content... recover?" — because a full-tree reserialize doesn't
reliably preserve everything Word's stricter OOXML parser depends on (e.g. the exact `xmlns:`
prefix set declared on the root, which the `mc:Ignorable` attribute references by name; a
regenerated prefix like `ns0:`/`ns5:` in place of the original is valid generic XML but can break
that reference). Generic-XML well-formedness is not the same bar as OOXML validity — passing the
first proves nothing about the second. **Fix: for any in-place patch to a real file, use targeted
string-level substitution on the raw XML text (regex or exact-substring replace) that touches only
the specific bytes that need to change, and leave every other byte — including the entire root
element's namespace declarations — untouched.** After patching, verify with more than "does it
parse": open the result with `python-docx` (`docx.Document(path)` succeeding is a stronger signal
than bare `ET.fromstring`, since python-docx exercises more of the real part relationships) in
addition to the `check_*()` script suite, before considering the file safe to hand back.

**Correction — all 6 story row-labels get a real number, not just "User & Function."** This was
wrong in an earlier pass, and wrong in a specific, checkable way: the rule was written after
checking only the *visible text* of Lending's and Transaction Reversal's row labels — since rows
2–6 showed no typed digits, they were assumed unnumbered. Checking `numPr` presence directly
(not just text) shows that's false: **all three real sources — the Master Template, Lending, and
Transaction Reversal — agree that all 6 row labels carry real `numPr`**, numbered sequentially:
`7.1.1. User & Function`, `7.1.2. Action`, `7.1.3. Result`, `7.1.4. Pre-Conditions`, `7.1.5.
Trigger`, `7.1.6. Expected`. This isn't template-vs-samples; all three independently confirm the
same design. The only defect found anywhere in any of the three is Transaction Reversal's row 0,
which has real `numPr` *and* also types `7.1.1.` redundantly as literal text on top of it.

**Content columns also get real numbers on every row, not just Action.** The Master Template
pre-sets up a dedicated numbered-list slot in *every* row's content column (`7.1.1.1`, `7.1.2.1`,
etc.), not only Action's multi-point cell. Generate at least one real numbered point per row's
content — more than one where the row genuinely has multiple distinct points (Action almost
always does; Result/Pre-Conditions/Trigger/Expected may have just one).

**Mechanism, verified three ways:**
- Lending's and Transaction Reversal's real generated documents both prove the row-label
  numbering works via real `numPr` on all 6 rows, continuing one shared list one level deeper
  than the story heading (`ilvl=2`) — this is a real, working, already-in-production mechanism,
  not a hypothetical one.
- The Master Template additionally shows the clean version with zero typed-digit noise anywhere:
  each row label is the *next* use of that same level, incrementing 1→2→3→4→5→6 in document
  order, and each row's content column continues one level deeper still (`ilvl=3`), auto-resetting
  to 1 each time the row-label level increments (Word resets deeper levels automatically when a
  shallower one on the same list advances — no manual reset logic needed).

**Implementation:** define one 4-level decimal list per story — reusing the section-heading list
is the simplest option (confirmed working for all 6 rows in both real generated documents); a
dedicated list scoped to that story (matching the Master Template's approach, with level 0/1
`start` hardcoded to the story's actual section/story numbers) is more robust for a generator,
since it doesn't depend on every earlier heading in the document having been emitted in the exact
right order first. Either way:
```
level 0 → section number   (e.g. 7)
level 1 → story number     (e.g. 1)
level 2 → row number       (1–6, one per row label, in document order:
                             User & Function, Action, Result, Pre-Conditions, Trigger, Expected)
level 3 → content point(s) within that row (1, 2, 3... as needed)
```
Apply `numbering: { reference, level: 2 }` to all 6 row-label paragraphs in document order, and
`numbering: { reference, level: 3 }` to every content-column paragraph, immediately following its
row's label so the level-3 counter resets to 1 correctly. Never type any of these digits as text
— same "no exceptions" rule as everywhere else in this document.

**The second numbering list's start value is not fixed at "7" — it equals whatever number
Features/Stories actually received.** Confirmed by comparing two real files: Transaction Reversal
(has a standalone Flow Chart section, so Features/Stories lands on 7 → Data Dictionary's list
`w:start="7"`) versus the Lending draft (no standalone Flow Chart heading, so Features/Stories
lands on 6 → Data Dictionary's list `w:start="6"`). Both are internally consistent — the "restart"
list's start value always matches the Features/Stories section number in that specific document,
it does not restart at a hardcoded 7. When generating: count how many top-level sections precede
Features/Stories in *this* document (Flow Chart is optional — see Section 4 in urs-format.md) and
set the second list's start value to that same number.

## Table of Contents / List of Figures / List of Tables — structural placement (not hyperlink color)

**Reported defects: "Table of Content" appeared as a numbered `1.1.` sub-heading under Document
Control, with List of Figures/Tables shoved in between the numbered subsections — instead of all
three sitting, unnumbered, before Section 1 even starts.**

**Explicit user decision: do not apply blue/underlined `Hyperlink` styling to ToC entries.** A
user reported the generated ToC came out blue and asked why — root cause: a genuine Word `TOC`
field (which is required — see below) applies the built-in `Hyperlink` character style
(`0563C1`, underlined) **by default**, and every real reference sample confirms this is standard
behavior, not a bug in the generator. A library's `TableOfContents` component (docx-js or
equivalent) does the same by default when it builds a real field. Nothing in this skill said to
override that default, so it carried straight through unchanged — this is the same "default
carries through unless explicitly overridden" mechanism already documented for fonts.

**The fix must be an explicit override, not just an instruction to "not do" the default:**
generate the real `TOC` field via docx-js's `TableOfContents` (still the right generation-time
approach — see below), then explicitly set every entry run's color to `000000` (black) with
`underline: none`, overriding whatever the field/component defaults to. Don't rely on the library
happening to default to plain — force it.

**The field must still be a genuine, live Word `TOC` field underneath in the final delivered
file** — explicit, repeated user requirement: it must behave exactly like a TOC inserted by hand in
Word, updatable later via right-click → Update Field after editing. Two real LOLC reference files
happen to contain static (already unlinked) ToC/LoF/LoT entries instead — but that's because a human
had already run them through one real Word update-and-save cycle at some point, not evidence that
static is the target shape to generate. Generate via `TableOfContents` at build time, then in
`postprocess.py`: fill its cache with real entries/real bookmarks/real Word-computed page numbers,
strip only the extraneous `<w:sdt>` content-control wrapper docx-js adds (a native Word TOC field
has none), and clear the stale `w:dirty` flag now that the cache is genuinely correct — see the
section below ("Table of Content / List of Figures / List of Tables must be genuine, live, updatable
Word fields") for the full mechanism and why.

**If generating with docx-js's `TableOfContents` component, its `alias` constructor argument is
NOT visible body text** — it's an internal Word content-control label, only visible in Word's own
editing UI, not rendered on the page. Real samples have an actual, separate `Heading1`-styled
paragraph with the literal text "Table of Content" / "List of Figures" / "List of Tables" placed
immediately before each field — generate that paragraph explicitly; don't assume the `alias` covers
it. **For List of Figures/Tables specifically, use the `captionLabelIncludingNumbers` option, not
`captionLabel`** — `captionLabel` builds `\a "Figure"`, which omits the figure number entirely
(shows only the caption text); `captionLabelIncludingNumbers` builds `\c "Figure"`, which is what
real samples actually show ("Figure 1 - Flowchart..." with the number). Confirmed by reading the
library's own source, not assumed from memory of Word field syntax. Also: a spacer/blank paragraph
inserted for the exact 0/1/2-empty-paragraph spacing below must contain **no run at all** — a
`TextRun` with empty-string text (`""`) still produces a `<w:t>` element, which several of this
file's own check scripts treat as "has text," so it won't count as an empty spacer even though it
looks empty. Use a paragraph with zero children, not a run containing an empty string.

**docx-js's `SimpleField` (used for `FILENAME`/`PAGE`/`NUMPAGES`/`SEQ` fields) wraps its cached
value in a bare inner `<w:r>` with no `rPr` at all** — it does not inherit the surrounding
`TextRun`'s font/size/color, so a cached field value renders in the theme default until Word
recalculates it. Patch the specific `<w:fldSimple w:instr="...">...</w:fldSimple>` run directly
after generation with the same formatting as its surrounding text; there is no constructor option
to set this via the public API. Confirmed on a real generated file (both a `SEQ Figure` caption
number and a footer's `FILENAME`/`PAGE`/`NUMPAGES` fields all needed this).

**The header logo specifically is not a floating image in any real reference file — it's a plain
inline image in its own paragraph (see Header & Footer above).** Using a floating/anchored image
there instead is what caused the two defects below in the first place; don't reach for `floating`
unless a specific image genuinely needs absolute page positioning or text wrap-around, which the
header logo does not.

**Embedding a floating image via docx-js (e.g. a header/footer logo) surfaced two independent real
defects on a single real generated file, both producing the same hard failure** ("Word experienced
an error trying to open the file" — a harder failure than the "unreadable content, recover?" prompt
seen for schema-looseness elsewhere in this file). Fixing the first alone did not resolve the
failure — both had to be found and fixed before the file opened. Check both, not just one, any time
a floating image is involved:

1. **Relationship-ID generator can emit `rId0` instead of `rId1`** when the image is embedded in an
   otherwise-empty relationship context (confirmed for a header containing only one image, no other
   relationships). Every real reference file checked this session starts numbering at `rId1`; none
   use `rId0`. Fix: check the generated part's `.rels` file after generation and renumber `rId0` →
   `rId1` (and its matching `r:embed`/`r:id` reference) if present.
2. **`floating.wrap` set to `TextWrappingType.TIGHT` (or `THROUGH`) generates a bare, self-closed
   `<wp:wrapTight/>` with no `<wp:wrapPolygon>` child** — but per the OOXML schema, `CT_WrapTight`
   requires exactly one `wrapPolygon` child (`minOccurs="1"`, not optional); a `wrapTight` without
   one is a genuine schema violation, not a stylistic gap, and is a very plausible cause of a hard
   open failure on its own. docx-js does not appear to generate the polygon automatically for this
   option. Fix: use `TextWrappingType.NONE` (`<wp:wrapNone/>`, which has no required children)
   instead, unless the image genuinely needs text to wrap tightly around its visible silhouette —
   for a `behindDocument: true` decorative image (a logo sitting behind body text), `NONE` is both
   simpler and visually equivalent, since the image doesn't interact with text flow either way.

**`python-docx` opening the file successfully is not evidence either of these is fine** — it opened
without complaint on the exact file Word refused to open at all, for both defects independently;
python-docx does not validate to the same strictness Word's own parser does, a lesson already
learned once this session for full-tree ElementTree reserialization and now confirmed twice more
for two unrelated defect classes. Also worth setting explicitly: docx-js's `ImageRun` leaves
`wp:docPr`'s `name`/`descr`/`title` attributes empty unless an `altText` option is passed — real
reference files always have a real name (e.g. `"Picture 10"`) here; pass `altText: { name, description,
title }` explicitly rather than leaving them blank, even though this specific gap is lower-confidence
as a hard-failure cause than the two above.

### A third hard-open-failure cause: `w14:paraId` / `wp14:anchorId` / `wp14:editId` must be valid 8-digit hex

Same failure class as `rId0` and the missing `wrapPolygon` above — a schema-invalid attribute value
that produces the same hard, generic failure ("Word experienced an error trying to open the file.
Try these suggestions: Check the file permissions... Open the file with the Text Recovery
converter."), not a rendering/stylistic gap — but a different, previously-undocumented root cause,
found while hand-splicing new paragraphs/images directly into an existing real `.docx` via raw XML
edits (not docx-js) rather than generating fresh.

Every one of `<w:p w14:paraId="...">`, `<wp:inline wp14:anchorId="..." wp14:editId="...">` is typed
`ST_LongHexNumber` in the OOXML schema — it must match `^[0-9A-Fa-f]{8}$`, exactly 8 hex digits, no
exceptions. An "invented" value that happens to contain a non-hex letter (e.g. `6A1K0001`,
`6A1L0004` — `K` and `L` are not hex digits) is schema-invalid and Word refuses to open the file at
all, with no more specific diagnostic than the generic message above.

**Confirmed via a minimal reproduction ladder, isolating the exact cause:**
1. A relationships-and-media-only change with no `document.xml` edit at all opened fine.
2. Adding one single new image paragraph with an invalid-hex `paraId` reproduced the hard-open
   failure in isolation — nothing else in the file had changed.
3. Switching that same paragraph's `paraId` to valid hex (e.g. `6A1C0001`), with everything else
   left untouched, fixed it immediately.

**Fix:** when hand-authoring any new `w14:paraId`, `wp14:anchorId`, or `wp14:editId` value for a
spliced-in paragraph or image, generate real 8-digit hex (e.g. from a random 32-bit value formatted
as `%08X`), never a string that merely *looks* like an ID. `check_hex_ids()` below scans the
generated `document.xml` for every occurrence of these three attributes and asserts each one is
exactly 8 hex characters — treat any `FAIL` from it exactly like a `FAIL` from `check_numbering()`:
fix the specific attribute and re-run, don't hand-wave it as cosmetic.

**docx-js's `Table` constructor defaults the `borders` option to `{}`, not `undefined`, when it's
omitted** — and `{}` is truthy, so `TableProperties` still emits a full default `<w:tblBorders>`
(single, size 4, color `"auto"`) in the table's own `tblPr` even when no `borders` option was ever
passed. This matters specifically for any table using Mechanism 1 (a named style like
`GridTable4-Accent3`, meant to supply its own borders with no manual override): an explicit
`tblPr`-level `tblBorders` always wins over a table style's own border definition (direct
formatting beats style, standard OOXML cascade), so the style's confirmed `C9C9C9` borders get
silently replaced by a plain `"auto"` grid — the header shading still looks right (that part
correctly comes from the style) but the table's border color is wrong, and generating this way
defeats the entire point of referencing the named style. There is no public docx-js option to
suppress this default (passing `borders: TableBorders.NONE` explicitly removes ALL borders,
including the style's, which is a different, worse, defect). Confirmed as the actual cause of a
real "Data Dictionary not formatted properly" report: the fix has to be a post-generation XML
patch — for each table whose `tblPr` contains a `GridTable4-Accent3` (or any other
manual-borders-not-wanted) `tblStyle` reference, strip the `<w:tblBorders>...</w:tblBorders>`
block docx-js inserted, leaving the style to supply borders on its own, exactly like the real
reference file (which has no `tblBorders` element at all in these tables' `tblPr`).

**Mechanism 1 tables need the named style's own definition injected into `styles.xml`, not just a
`style: "GridTable4-Accent3"` reference on the `Table`.** Some built-in Word table style IDs (e.g.
`TableGrid`) resolve correctly by name alone with no explicit `<w:style>` definition present.
`GridTable4-Accent3` is a themed style — referencing it by ID alone leaves its header color
dependent on docx-js's own default theme's `accent3` color, which is not guaranteed to match the
real reference file's `A5A5A5` grey. Fix: inject the style's full definition (extracted verbatim
from a real file's `styles.xml`) as a post-generation patch, before `</w:styles>`, if not already
present — it bakes literal color fallbacks (`A5A5A5`, `C9C9C9`, `EDEDED`) alongside the theme
references, so the header renders the confirmed real color regardless of which theme the generator
shipped.

**`TOC1`/`TOC2`/`TableofFigures` paragraph styles need their definitions injected into `styles.xml`
too, same as `GridTable4-Accent3` above — referencing a style ID by name is not enough on its own.**
docx-js sets `pStyle="TOC1"`/`"TOC2"`/`"TableofFigures"` on ToC/LoF/LoT entry paragraphs but never
emits a `<w:style>` definition for any of them, so Word falls back to its generic built-in latent
style, which does not carry the real file's own indent override. Confirmed by direct comparison
against `Blacklist_Rule_to_Transaction_Event_Mapping_V0.1.docx`'s own `styles.xml`: it explicitly
defines `TOC1` (`spacing after=100`, no indent), `TOC2` (`spacing after=100`, `ind left="220"` —
this is what visually separates a `1.` entry from its `1.1.` children), and `TableofFigures`
(`spacing after=0`, no indent). Without injecting these, every ToC/LoF/LoT entry rendered flush
against the same left margin regardless of level — a real visual defect, confirmed by actually
opening the generated file (not something any of the 13 mechanical checks catch, since they check
structure, not style-definition presence). Fix: inject all three verbatim into `styles.xml` in
`postprocess.py`, same pattern as `GRIDTABLE4_STYLE_XML`.

**Cover-page table cells carry no `tcMar` (cell margin) override at all in the real reference
file** — confirmed via direct XML inspection (`Blacklist_Rule_to_Transaction_Event_Mapping_V0.1.docx`),
relying entirely on the `TableGrid` style's own default cell margins. The shared cell helpers used
elsewhere in the body (e.g. a `shadedCell`/`plainCell` pair with an explicit `margins:
{top:80,bottom:80,left:100,right:100}` override) render noticeably more padded than the real cover
table when reused there — build the cover table's cells with a dedicated helper that omits the
margins override, rather than reusing a body-table cell helper that happens to produce visually
similar-looking cells.

**"Table of Content", "List of Figures", and "List of Tables" are never numbered, and always
sit before Section 1's numbered sequence begins — never interleaved with it.** Confirmed directly:
all three are `Heading1`-styled paragraphs with **no `numPr` at all** (not `ilvl=0` on the section
list, not any other list — genuinely no numbering), positioned in the body strictly in this order,
strictly before the first real numbered heading (`1. Document Control` or equivalent):
```
Table of Content   [Heading1, no numPr]
  ↳ ToC field
List of Figures    [Heading1, no numPr]
  ↳ field entries
List of Tables     [Heading1, no numPr]
  ↳ field entries
1. Document Control  [Heading1, numPr ilvl=0 — numbering starts here, not before]
  1.1. Document Information  [Heading1/2, numPr ilvl=1]
  ...
```
If "Table of Content" ends up with `numPr` applied (so it renders as `1.1.` and gets sorted into
the numbered sequence alongside "Document Information"), that's a generation-order bug: the
front-matter block was built as part of the same numbered-heading loop as Section 1's real
subsections instead of as a separate, deliberately-unnumbered block emitted first. Generate these
3 headings as their own step, explicitly without any `numbering` property, before starting the
Section 1 heading loop.

## Embedding a non-Office file as a double-clickable icon — a different mechanism from embedding a picture

New territory for this skill, confirmed by grepping the whole prior history of this file for
"OLEObject", "ProgID", and "Package" — zero hits before this session. The "Embedding a floating
image via docx-js" gotchas above are about embedding *pictures*; embedding an arbitrary *file*
(e.g. a standalone `.html` prototype) as a double-clickable icon inside the document is a
structurally different OOXML mechanism, and neither the picture-embedding pattern above nor an
Office-document-embed pattern (`ProgID="Word.Document.12"` etc.) transfers to it.

**What does NOT work (tried first) — looks structurally plausible, opens without error, but the
icon does nothing when double-clicked:** a relationship of type
`http://schemas.openxmlformats.org/officeDocument/2006/relationships/package` pointing directly at
the raw target file (e.g. `embeddings/MyFile.html`), paired with a hand-written object element
copied from a real Word/Excel-embed example:
```xml
<w:object>
  <v:shapetype .../>
  <v:shape ...><v:imagedata r:id="{icon_rid}"/></v:shape>
  <o:OLEObject Type="Embed" ProgID="Package" ShapeID="..." DrawAspect="Icon" ObjectID="..." r:id="{pkg_rid}">
    <o:FieldCodes>\s</o:FieldCodes>
  </o:OLEObject>
</w:object>
```
The `<o:FieldCodes>` child is the tell — it's copied from a pattern for embedding *other Office
documents* (where `ProgID` is something like `Word.Document.12`), and that pattern simply does not
apply to a generic-file `Package` embed. The object renders visually fine and the file opens
without complaint; it just isn't wired to anything real.

**What actually works, confirmed by using Word itself (via COM automation) to perform the real
"Insert Object > Create from File" action and then inspecting the exact XML/relationships/parts it
produces:**
- The relationship type must be
  `http://schemas.openxmlformats.org/officeDocument/2006/relationships/oleObject` — **not**
  `.../package` — and its target is a compound binary blob at `word/embeddings/oleObjectN.bin`,
  **not the raw source file**. This `.bin` is a real OLE1 "Native" Packager stream (packager
  metadata — friendly name, source path — plus the actual file bytes, wrapped in Windows' own
  compound-file packager format). There is no practical way to hand-construct this binary
  correctly; it has to come out of the real OS/Office OLE machinery.
- The icon shown is a separate `image/x-emf` part (`word/media/imageN.emf`), auto-generated by
  Windows from the target file's own shell icon association — not a custom PNG.
- The actual `<o:OLEObject>` element for a `ProgID="Package"` embed is **self-closing**:
  `<o:OLEObject Type="Embed" ProgID="Package" ShapeID="..." DrawAspect="Icon" ObjectID="..." r:id="{oleObjectRid}"/>`
  — with **no** `<o:FieldCodes>` child at all. That child only belongs to embedded-Office-document
  `ProgID`s.
- The `<v:shape>` needs an `o:ole=""` attribute present, in addition to the usual
  `type="#_x0000_t75"` and `<v:imagedata r:id="{iconRid}" o:title=""/>`.

**The correct, reliable recipe: don't hand-author this at all. Use Word COM automation to perform
the real embed:**
```
Selection.InlineShapes.AddOLEObject(ClassType:="", FileName:="<absolute path to the file>", _
    LinkToFile:=False, DisplayAsIcon:=True, IconFileName:="<optional>", _
    IconIndex:=<optional>, IconLabel:="<optional caption>")
```
If inserting into an *already-generated* `.docx` (e.g. one this skill built via docx-js) rather
than a document Word is authoring from scratch: open the target `.docx` via COM, use
`Selection.Find` (or a bookmark) to navigate to the exact paragraph, delete any placeholder
paragraph sitting there, call `AddOLEObject` at that `Range`, set
`.Range.ParagraphFormat.Alignment` if centering is needed, then `doc.Save()`.

**This does require a real Word-COM `.Save()` call — that is not a universal contradiction of the
"no COM Save" rule documented elsewhere in this file (see the Word-COM destructive-save warning in
the "Why past output drifted" section and the numbering section's `LevelSuffix.NOTHING` fallback):
that regression is specific to docx-js-originated files whose `styles.xml` has hand-injected
non-standard style definitions** (theme injection, manual `GridTable4-Accent3` redefinition,
`TableNormal` injection — see the Table styles sections above) that Word's own re-serialization
doesn't understand and silently drops on save. A genuinely Word-native file — one whose entire
lineage has always been saved by real Word, never docx-js — does not carry that risk, since Word
already fully understands its own structure end to end. Document this distinction explicitly
wherever it comes up again: "no COM Save" is not a universal rule, it's specific to docx-js-
originated files with hacked-in `styles.xml` content. After a Save on a genuinely Word-native file,
still verify nothing else was altered — compare *content*, not raw bytes, since Word's own
re-serialization changes whitespace/attribute order harmlessly (parse and compare `comments.xml`'s
actual `(id, author, text)` tuples before vs. after, confirm `python-docx` still opens the file,
confirm expected table/paragraph counts didn't change).

**Testing caveat, worth knowing before wasting time on it:** verifying the embed actually
*activates* by calling `InlineShape.OLEFormat.DoVerb(0)` (the programmatic equivalent of
double-clicking) on a `ProgID="Package"` object triggers Windows' own native "this file type could
potentially harm your computer, are you sure you want to open it?" security prompt — a real
OS-level modal dialog that headless/hidden (`Application.Visible = False`) COM automation cannot
click through, so the call just hangs indefinitely. This is expected, not a bug — a real
interactive user double-clicking the icon in a visible Word window sees (and can click through) the
same prompt, then the file opens in its default associated app. Don't waste time trying to suppress
this or mistake the hang for a broken embed. Verify without hanging by checking structure instead:
confirm the `oleObject` relationship type, confirm the `.bin` part exists and has a non-trivial
size, and treat "built via the real Word `AddOLEObject` call above" as the reliability guarantee
rather than trying to verify a hand-built object's payload byte-for-byte (a `sha256` of the source
file's bytes is not reliably findable inside the `.bin` blob, since the packager format doesn't
store the payload byte-identically-inline in an easily-diffable way).

## Adding tracked changes to an existing, already-reviewed .docx without disturbing its Word comments

Also new territory for this skill — previously it only ever generated fresh documents with no
revision or comment history. The scenario: a `.docx` already has real Word comment threads
(`word/comments.xml`, `word/commentsExtended.xml`, `word/commentsIds.xml`,
`word/commentsExtensible.xml`, `word/people.xml`) from a reviewer, and new content needs to go in as
visible tracked changes (`w:ins`/`w:del`) — so the reviewer sees exactly what changed — while every
comment thread stays completely intact.

**Before editing any paragraph, grep it for `commentRangeStart`, `commentRangeEnd`, and
`commentReference`.** If any of these anchors fall inside the text about to be touched, editing
that XML carelessly will orphan a comment — Word will either error or silently drop the anchor.
Confirm zero overlap before proceeding wherever possible; if a comment genuinely anchors inside the
text being changed, that requires careful preservation of the anchor elements around the edit, not
a blind text replacement.

**Two distinct tracked-change patterns — don't conflate them:**

1. **Inserting a brand-new paragraph** (e.g. a new image plus its own caption paragraph that didn't
   exist before): wrap the paragraph's run content in
   `<w:ins w:id="N" w:author="..." w:date="...">...</w:ins>`, **and separately** mark the paragraph
   mark itself as inserted via
   `<w:pPr>...<w:rPr><w:ins w:id="M" w:author="..." w:date="..."/></w:rPr></w:pPr>` — note this is
   `w:rPr` as a *child of `w:pPr`* (paragraph-mark run-properties, `CT_ParaRPr`), not a regular
   run's `w:rPr`. This self-closing `w:ins` must be the *first* child per `CT_ParaRPr`'s schema
   order, before any other run-property elements (`w:i`, `w:color`, etc.), though in practice it's
   usually the only child needed here. Skipping the paragraph-mark half still *renders* visually as
   tracked (Word tolerates it), but it isn't the fully-correct mechanism — do both halves.
2. **Editing existing text in place** (e.g. replacing one sentence with another inside a paragraph
   that already existed): mark the old run as deleted by wrapping it in
   `<w:del w:id="N" w:author="..." w:date="...">` and changing its `<w:t>` to `<w:delText>`
   (required — `w:del`'s content model does not accept `w:t`), then add a sibling
   `<w:ins w:id="M" w:author="..." w:date="...">` containing a normal new run with `<w:t>`. No
   paragraph-mark marking needed here, since the paragraph itself isn't new.
3. **A targeted substring change inside a longer sentence** (e.g. only two numbers change, the rest
   of the sentence is unchanged): split the original single run into multiple runs — unchanged
   plain run, `w:del` run for the old substring, `w:ins` run for the new substring, unchanged plain
   run, repeat as needed. This reads as a genuine, surgical reviewer edit rather than a wholesale
   paragraph rewrite, and is the more faithful/professional-looking result.

**To programmatically "Accept All Changes" afterward** (finalize the tracked edits into plain text)
**without** a Word-COM `Save()` round-trip — to sidestep the docx-js style-stripping risk documented
above, when the underlying file *is* docx-js-originated — do it as a pure regex pass over
`document.xml`:
1. Strip every self-closing paragraph-mark `<w:ins w:id="..." w:author="..." w:date="..."/>`.
2. Remove every `<w:del ...>...</w:del>` block wholesale (regex with `re.S`/DOTALL, non-greedy —
   the deleted content disappears, exactly like a real "Accept").
3. Unwrap every remaining `<w:ins ...>...</w:ins>` by replacing it with just its captured inner
   content (same DOTALL non-greedy regex technique).

Verify success by reopening in Word via COM (read-only, no Save) and confirming
`doc.Revisions.Count == 0`; also re-grep the raw XML for `<w:ins\b`/`<w:del\b` with a **tag-anchored**
regex — not a bare substring count. A plain substring match on `w:ins`/`w:del` produces false
positives against unrelated elements like `w:insideH`/`w:insideV`/`w:instrText`/`w:delText`
residue; always anchor on `<w:ins ` / `<w:ins/` / `<w:del ` etc., or better, parse and check element
names properly via `ElementTree`.

**To produce a comments-free copy of a reviewed file** (strip the review layer entirely, e.g. for
distributing a "clean" version): remove the five comment-related parts from the zip
(`word/comments.xml`, `word/commentsExtended.xml`, `word/commentsIds.xml`,
`word/commentsExtensible.xml`, `word/people.xml`), remove their `<Relationship>` entries from
`word/_rels/document.xml.rels`, remove their `<Override>` entries from `[Content_Types].xml`, and —
critically — remove every `<w:commentRangeStart .../>`, `<w:commentRangeEnd .../>`, and the
enclosing `<w:r>...<w:commentReference .../></w:r>` run (both the plain form and the form with
`<w:rPr><w:rStyle w:val="CommentReference"/></w:rPr>`) from `document.xml`, or Word will show a
repair prompt / the file will be structurally inconsistent. Verify via Word-COM open (read-only):
`doc.Comments.Count == 0` and no error/repair dialog.

## MANDATORY: verify numbering, fonts, colors, table styles, and front-matter/body spacing — don't eyeball any

**This exact defect was reported by a user after testing generated output**: numbers were correct
when first generated but behaved like plain text — editable, not renumbering on delete. The
instructions above already said "don't type digits" before that happened; a prose instruction
alone was not sufficient, because a generated document can look completely correct in a visual
review while still being wrong underneath (typed `"7.1.2.1."` and a real `numPr`-numbered `"1."`
render identically at a glance). **Visual review of the draft or a rendered preview cannot catch
this class of defect — it requires opening the actual XML.**

**The same failure class applies to the Table of Contents, List of Figures, and List of Tables.**
In every real sample these are genuine Word `TOC` fields (`fldChar begin` / `instrText" TOC \o
"1-3" \h \z \u"` / `fldChar separate` / cached result text / `fldChar end`) — not manually typed
lines with dot leaders and hardcoded page numbers. A typed-text ToC looks identical to a real one
when first generated, but can't be updated (right-click → Update Field) if content shifts, and is
the likely mechanism behind reported front-matter spacing problems too — see "Front-matter
spacing" in `urs-format.md` for the exact empty-paragraph defect this script's second check
catches. Run both checks after every generation, as part of STEP 2.5 Pass 2, before presenting the
file:

```python
import zipfile, re

def check_numbering(docx_path):
    # No exceptions: every typed multi-level decimal pattern in a <w:t> run is a defect,
    # including all 6 story row-label prefixes (User & Function, Action, Result, Pre-Conditions,
    # Trigger, Expected). The Master Template proves this is achievable with zero typed text on
    # any of the 6 (real numPr continuing one shared list at level 2); both real generated
    # samples under-implement this (only number the first row, and Transaction Reversal even
    # types that one redundantly alongside a non-functional numPr) — that's the shortcut to
    # avoid, not a pattern to reproduce. (An earlier version of this check exempted the row
    # label entirely; that was wrong — removed, then generalized to all 6 labels.)
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        xml_bytes = z.read('word/document.xml')
    xml = xml_bytes.decode('utf-8')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'

    # {1,4} not {2,4}: the narrower range only ever caught 3-5 segment typed numbers (story
    # sub-points like 7.1.2.1., deep headings like 1.1.1.) and structurally could not match a
    # 2-segment typed number (X.Y) at all — confirmed as a real gap, not a theoretical one, on two
    # independent real documents: a Blacklist URS had a whole sub-heading typed as literal text
    # ("10.1  Common Guide for FusionX", zero numPr) that this check reported as PASS every time
    # it ran, and re-testing the widened pattern against Transaction Reversal V1.0 — the file
    # treated as most-authoritative all session — surfaced a previously-undetected defect of its
    # own: two headings render as a REAL numPr-generated "7." run immediately followed by a
    # separate, literally-typed "2.1."/"3.1." run glued onto it, producing a visually complete
    # "7.2.1."/"7.3.1." where only the first segment is real. Verified the widened range adds zero
    # false positives on three other real files (Lending, XX Module template, Master Template —
    # all 0 matches, unchanged) before shipping this.
    #
    # Excludes Table of Contents / List of Figures / List of Tables entries: their cached
    # hyperlink text legitimately mirrors a heading's rendered number as plain text (that's how a
    # real TOC field's cached result works — it is not typed numbering on the actual heading,
    # which elsewhere in the body still uses real numPr). Confirmed as a real false-positive
    # source once the {1,4} widening above was tested against a real file: 10 matches, all of them
    # inside `<w:hyperlink w:anchor="_Toc...">` spans, zero real defects once excluded. Not every
    # real document wraps its TOC field in a `<w:sdt>` (this one didn't), so exclude by the
    # `_Toc`-anchored hyperlink span itself rather than assuming an sdt wrapper is present.
    toc_spans = [(m.start(), m.end()) for m in
                 re.finditer(r'<w:hyperlink w:anchor="_Toc[^"]*"[^>]*>.*?</w:hyperlink>', xml, re.S)]
    typed_numbers = [m.group(1) for m in re.finditer(r'<w:t[^>]*>\s*(\d+(?:\.\d+){1,4}\.)\s', xml)
                      if not any(s <= m.start() < e for s, e in toc_spans)]
    numPr_count = len(re.findall(r'<w:numPr>', xml))

    # Positive check: every one of the 6 row-label paragraphs must itself carry numPr — absence
    # of a typed number isn't enough proof; it could just as easily mean the number was dropped
    # entirely rather than generated as a real field.
    ROW_LABELS = ['User\\s*&\\s*Function', 'Action', 'Result', 'Pre-Conditions', 'Trigger', 'Expected']
    root = ET.fromstring(xml_bytes)
    missing_numpr_labels = []
    for el in root.iter(f'{Wns}p'):
        text = ''.join(el.itertext()).strip()
        for label_pattern in ROW_LABELS:
            if re.match(r'^\s*(\d+(\.\d+)*\.\s*)?' + label_pattern + r'\s*$', text, re.I):
                if el.find(f'{Wns}pPr/{Wns}numPr') is None:
                    missing_numpr_labels.append(text[:50])
                break

    if typed_numbers:
        print(f"FAIL: {len(typed_numbers)} typed numbering strings found in text runs, e.g. {typed_numbers[:5]}")
        print("These paragraphs must be regenerated using numbering:{reference, level}, not typed text.")
    elif missing_numpr_labels:
        print(f"FAIL: {len(missing_numpr_labels)} story row label(s) have no typed number (good) but also no numPr (bad) — the number was dropped instead of generated as a real field: {missing_numpr_labels}")
    elif numPr_count == 0:
        print("FAIL: no <w:numPr> found anywhere in the document — numbering was likely dropped entirely.")
    else:
        print(f"PASS: no typed numbering patterns found anywhere, including all 6 row labels; {numPr_count} real numPr-numbered paragraphs present.")

def check_numbering_gap(docx_path):
    # Catches the defect confirmed on a real generated file (Blacklist Rule to Transaction Event
    # Mapping URS): explicit `w:suff val="nothing"` on a used list level (the documented fallback
    # for a Word-COM-Save pipeline, not the default) combined with a literal leading space/tab
    # typed into the paragraph's first text run — together these produce a first-line gap that
    # doesn't match the wrapped continuation line's hanging-indent alignment.
    #
    # Deliberately does NOT check `ind left == hanging` generally — tested against Transaction
    # Reversal V1.0 (ground truth) and it false-fails: that equality only holds for the specific
    # story-subpoint chain (level 3), not for headings or other lists, which validly use
    # hanging < left (e.g. Word's ordinary single-level default, 720/360). A check that fails the
    # reference file it's meant to validate against is worse than no check — dropped.
    import xml.etree.ElementTree as ET
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    with zipfile.ZipFile(docx_path) as z:
        doc_bytes = z.read('word/document.xml')
        num_bytes = z.read('word/numbering.xml')
    root = ET.fromstring(doc_bytes)
    num_root = ET.fromstring(num_bytes)

    numid_to_abs = {}
    for n in num_root.findall(f'{Wns}num'):
        ref = n.find(f'{Wns}abstractNumId')
        if ref is not None:
            numid_to_abs[n.get(f'{Wns}numId')] = ref.get(f'{Wns}val')

    level_info = {}  # (absid, ilvl) -> (suff, left, hanging)
    for absnum in num_root.findall(f'{Wns}abstractNum'):
        absid = absnum.get(f'{Wns}abstractNumId')
        for lvl in absnum.findall(f'{Wns}lvl'):
            suff_el = lvl.find(f'{Wns}suff')
            suff = suff_el.get(f'{Wns}val') if suff_el is not None else 'tab'  # implicit default
            ind_el = lvl.find(f'{Wns}pPr/{Wns}ind')
            left = ind_el.get(f'{Wns}left') if ind_el is not None else None
            hanging = ind_el.get(f'{Wns}hanging') if ind_el is not None else None
            level_info[(absid, lvl.get(f'{Wns}ilvl'))] = (suff, left, hanging)

    suff_nothing = set()
    used_levels = set()
    for p in root.iter(f'{Wns}p'):
        numPr = p.find(f'{Wns}pPr/{Wns}numPr')
        if numPr is None:
            continue
        numid_el = numPr.find(f'{Wns}numId')
        ilvl_el = numPr.find(f'{Wns}ilvl')
        if numid_el is None:
            continue
        numid = numid_el.get(f'{Wns}val')
        ilvl = ilvl_el.get(f'{Wns}val') if ilvl_el is not None else '0'
        absid = numid_to_abs.get(numid)
        if absid is None:
            continue
        key = (absid, ilvl)
        used_levels.add(key)
        suff, left, hanging = level_info.get(key, (None, None, None))
        if suff == 'nothing':
            suff_nothing.add(key)

    # Deliberately requires the run to be >=2 chars of PURE whitespace, matching the documented
    # fallback recipe's literal `TextRun({text: "  "})` exactly — a single leading space is common,
    # harmless Word run-splitting (e.g. a row label like "User & Function" can land its first
    # `<w:t>` as just " " purely from how Word split the runs while it was typed/edited; confirmed
    # false-positive on Lending V0.1 when this checked for any leading whitespace instead of a
    # dedicated >=2-char whitespace-only run).
    leading_space_paragraphs = []
    for p in root.iter(f'{Wns}p'):
        if p.find(f'{Wns}pPr/{Wns}numPr') is None:
            continue
        for r in p.findall(f'{Wns}r'):
            t = r.find(f'{Wns}t')
            if t is not None and t.text:
                if t.text.strip() == '' and len(t.text) >= 2:
                    leading_space_paragraphs.append(''.join(p.itertext()).strip()[:50])
                break  # only check the first run that actually has text

    problems = []
    if suff_nothing:
        problems.append(f'{len(suff_nothing)} list level(s) use suff="nothing" (the fallback recipe): {sorted(suff_nothing)}. Only acceptable as a documented [EXCEPTION] for a confirmed Word-COM-Save pipeline — the default recipe is suff="tab".')
    if leading_space_paragraphs:
        problems.append(f"{len(leading_space_paragraphs)} numbered paragraph(s) have a literal leading space/tab typed into their first text run, e.g. {leading_space_paragraphs[:5]}. This belongs only in the documented COM-Save fallback; using it as the default produces a first-line gap that doesn't match the wrapped continuation line's hanging-indent alignment.")

    if problems:
        print("FAIL: " + " | ".join(problems))
    else:
        print(f'PASS: all {len(used_levels)} used list level(s) use suff="tab", and no numbered paragraph has a literal leading space/tab.')

def check_heading_numbering(docx_path):
    # check_numbering()'s regex only catches 3-5 level typed numbers (matches story sub-points
    # like "7.1.2.1."). Section headings ("1.", "1.1.", "1.6.") are 1-2 level and would slip
    # past that regex entirely if typed as plain text — this check covers that gap directly by
    # inspecting Heading1/2/3 paragraphs specifically.
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        xml_bytes = z.read('word/document.xml')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    root = ET.fromstring(xml_bytes)
    kids = list(root.find(f'{Wns}body'))

    # These are legitimately unnumbered even though they're Heading1-styled: the cover-page
    # title (always the first Heading1 in the body) and the front-matter labels, which are not
    # part of the numbered "1. Document Control" onward sequence.
    UNNUMBERED_LABELS = {'Table of Contents', 'Table of Content', 'List of Figures', 'List of Tables'}
    seen_first_heading = False

    problems = []
    for el in kids:
        if el.tag != f'{Wns}p':
            continue
        style_el = el.find(f'{Wns}pPr/{Wns}pStyle')
        style = style_el.get(f'{Wns}val') if style_el is not None else None
        if style not in ('Heading1', 'Heading2', 'Heading3'):
            continue
        text = ''.join(el.itertext())
        if not text.strip():
            continue  # empty heading-styled spacer paragraphs are checked elsewhere
        if not seen_first_heading:
            seen_first_heading = True
            continue  # cover-page title — legitimately unnumbered, skip
        if text.strip() in UNNUMBERED_LABELS:
            continue
        has_numpr = el.find(f'{Wns}pPr/{Wns}numPr') is not None
        typed_prefix = re.match(r'^\s*\d+(\.\d+)*\.\s', text)
        if typed_prefix:
            problems.append(f'"{text[:50]}" — the number ("{typed_prefix.group(0).strip()}") is typed into the heading text itself, not generated by numPr')
        elif not has_numpr:
            problems.append(f'"{text[:50]}" — {style} paragraph has no numPr at all; it will display with no section number')

    if problems:
        print(f"FAIL: {len(problems)} heading(s) with broken numbering —")
        for p in problems:
            print("  - " + p)
    else:
        print("PASS: every numbered heading paragraph uses real numPr; no typed number prefixes found.")

def check_second_list_start(docx_path):
    # The Data-Dictionary-onward heading list must independently restart at whatever section
    # number Features/Stories actually landed on (see "duplicate 7." note above) — not hardcode 7,
    # and not just continue Features/Stories' own list (which would silently produce the wrong,
    # sequential 8/9/10... instead of the confirmed real-template restart quirk).
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        doc_bytes = z.read('word/document.xml')
        num_bytes = z.read('word/numbering.xml')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    root = ET.fromstring(doc_bytes)
    kids = list(root.find(f'{Wns}body'))

    def para_style(el):
        s = el.find(f'{Wns}pPr/{Wns}pStyle')
        return s.get(f'{Wns}val') if s is not None else None
    def numid_of(el):
        n = el.find(f'{Wns}pPr/{Wns}numPr/{Wns}numId')
        return n.get(f'{Wns}val') if n is not None else None
    def ilvl_of(el):
        n = el.find(f'{Wns}pPr/{Wns}numPr/{Wns}ilvl')
        return n.get(f'{Wns}val') if n is not None else None

    # Count top-level (ilvl=0) sections only up to and including Features/Stories — sections
    # AFTER it (Data Dictionary, E2E Impact, ...) are ilvl=0 too, on the second list, and must
    # NOT be counted here or the expected total comes out wrong (confirmed bug: counting them
    # inflated "expected" from 6 to 10 on a real file before this fix).
    expected, fs_numid, dd_numid, seen_fs, counting = 0, None, None, False, True
    for el in kids:
        if el.tag != f'{Wns}p' or para_style(el) != 'Heading1':
            continue
        text = ''.join(el.itertext()).strip()
        if not text:
            continue
        if counting and ilvl_of(el) == '0':
            expected += 1
        if text == 'Features/Stories':
            fs_numid, seen_fs, counting = numid_of(el), True, False
        if seen_fs and text == 'Data Dictionary' and dd_numid is None:
            dd_numid = numid_of(el)

    if not dd_numid:
        print("FAIL: could not find a numbered 'Data Dictionary' heading — inspect manually.")
        return
    if dd_numid == fs_numid:
        print(f"FAIL: 'Data Dictionary' reuses Features/Stories' own numId ({dd_numid}) instead of an independent second list — it will number sequentially (8., 9., ...) instead of correctly restarting.")
        return

    # ElementTree-based lookup, not a raw regex on the XML text: a regex anchored to exact
    # whitespace (e.g. no space before `/>`) false-FAILs on any numbering.xml that's been
    # reserialized by ElementTree itself (which writes `<w:abstractNumId w:val="11" />` — a space
    # before `/>` — instead of the original tool's `.../>` with no space); both are valid,
    # identical XML, and Word doesn't care, but a naive regex does. Confirmed as a real false FAIL
    # on a file patched via ElementTree, where the underlying numbering was actually correct.
    num_root = ET.fromstring(num_bytes)
    numid_to_abs = {}
    for n in num_root.findall(f'{Wns}num'):
        ref = n.find(f'{Wns}abstractNumId')
        if ref is not None:
            numid_to_abs[n.get(f'{Wns}numId')] = ref.get(f'{Wns}val')
    abs_id = numid_to_abs.get(dd_numid)
    if abs_id is None:
        print(f"FAIL: could not resolve numId {dd_numid} to an abstractNum — inspect manually.")
        return
    actual = None
    for absnum in num_root.findall(f'{Wns}abstractNum'):
        if absnum.get(f'{Wns}abstractNumId') == abs_id:
            lvl0 = absnum.find(f'{Wns}lvl[@{Wns}ilvl="0"]')
            start_el = lvl0.find(f'{Wns}start') if lvl0 is not None else None
            actual = int(start_el.get(f'{Wns}val')) if start_el is not None else None
            break

    if actual != expected:
        print(f"FAIL: Data Dictionary's second list starts at {actual}, but Features/Stories is section {expected} — these must match.")
    else:
        print(f"PASS: Data Dictionary's second list correctly restarts at {actual}, matching Features/Stories' section number.")

def check_front_matter(docx_path):
    # Rewritten to use ElementTree over top-level body children only (matching the other
    # newer checks) instead of a flat regex paragraph split. The flat regex version had a real
    # bug: it doesn't respect the <w:sdt> boundary around the ToC field, so it flattened that
    # field's ~30 internal cached entries into the top-level sequence and mis-flagged one of the
    # field's own internal artifact paragraphs as a "gap between sections" (a confirmed false
    # positive on a real V1.0 file that manual inspection showed had zero actual gap).
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        xml_bytes = z.read('word/document.xml')
    xml = xml_bytes.decode('utf-8')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'

    # Real ToC/List of Figures/List of Tables are TOC fields, not typed text.
    # Order-agnostic: a TOC field's switches (\o, \h, \z, \u, \a, \c...) can legitimately appear
    # in any order — confirmed on a real generation where a library emitted `TOC \h \o "1-2"`
    # (hyperlink switch before the heading-range switch), which a rigid `'TOC \o' in xml`
    # substring check misses even though the field is completely valid. Match "TOC" followed by
    # the target switch anywhere before the next tag, not immediately.
    toc_field = bool(re.search(r'TOC\b[^<]*\\o', xml))
    lof_field = bool(re.search(r'TOC\b[^<]*\\c[^<]*(?:"Figure"|&quot;Figure&quot;)', xml))
    lot_field = bool(re.search(r'TOC\b[^<]*\\c[^<]*(?:"Table"|&quot;Table&quot;)', xml))
    if not (toc_field and lof_field and lot_field):
        missing = [n for n, ok in [("Table of Contents", toc_field), ("List of Figures", lof_field), ("List of Tables", lot_field)] if not ok]
        print(f"FAIL: not real Word fields (or missing outright): {missing}. These must be generated as native TOC fields, not typed dot-leader text.")
        return

    root = ET.fromstring(xml_bytes)
    kids = list(root.find(f'{Wns}body'))

    def para_style(el):
        s = el.find(f'{Wns}pPr/{Wns}pStyle')
        return s.get(f'{Wns}val') if s is not None else None
    def is_heading_text(el, texts):
        return el.tag == f'{Wns}p' and para_style(el) in ('Heading1', 'Heading2') \
            and ''.join(el.itertext()).strip() in texts
    def is_empty(el):
        return el.tag == f'{Wns}p' and el.find(f'.//{Wns}t') is None

    def find_idx(texts):
        for i, el in enumerate(kids):
            if is_heading_text(el, texts):
                return i
        return None

    toc_i = find_idx({'Table of Content', 'Table of Contents'})
    lof_i = find_idx({'List of Figures'})
    lot_i = find_idx({'List of Tables'})
    next_section_i = None
    if lot_i is not None:
        for i in range(lot_i + 1, len(kids)):
            el = kids[i]
            if el.tag == f'{Wns}p' and para_style(el) in ('Heading1', 'Heading2') and ''.join(el.itertext()).strip():
                next_section_i = i
                break

    if None in (toc_i, lof_i, lot_i, next_section_i):
        print("FAIL: could not locate all of Table of Content / List of Figures / List of Tables / next section heading — inspect manually.")
        return

    # Reported defect: "Table of Content" rendered as a numbered "1.1." sub-heading under
    # Document Control instead of sitting unnumbered before Section 1. Confirmed from real files:
    # these 3 headings never carry numPr, and always precede the first real numbered heading.
    numbered_front_matter = [
        ''.join(kids[i].itertext()).strip()
        for i in (toc_i, lof_i, lot_i)
        if kids[i].find(f'{Wns}pPr/{Wns}numPr') is not None
    ]
    if numbered_front_matter:
        print(f"FAIL: front-matter heading(s) incorrectly numbered: {numbered_front_matter} — these must have no numPr at all and must be generated as their own step, before Section 1's numbered heading loop starts, not as part of it.")
        return
    if next_section_i is not None and kids[next_section_i].find(f'{Wns}pPr/{Wns}numPr') is None:
        print(f"FAIL: the first heading after List of Tables ({''.join(kids[next_section_i].itertext()).strip()[:40]!r}) has no numPr — Section 1 should start numbering immediately after the front matter, not continue unnumbered.")
        return

    # Active check, not just a documented preference: a user reported the generated ToC coming
    # out blue by default (the library's TableOfContents component applies Hyperlink styling
    # automatically when building a real field, same as every real reference sample does) — an
    # explicit override was added to the spec, but a written rule alone doesn't stop a future
    # generation from leaving the library default in place again. Verify the override actually
    # landed: no Hyperlink-styled run and no 0563C1-colored run anywhere in the front-matter
    # region (ToC field through the end of List of Tables' entries).
    hyperlink_found = False
    for i in range(toc_i, next_section_i):
        for el in kids[i].iter():
            tag = el.tag.replace(Wns, '')
            if tag == 'rStyle' and el.get(f'{Wns}val') == 'Hyperlink':
                hyperlink_found = True
            if tag == 'color' and el.get(f'{Wns}val', '').upper() == '0563C1':
                hyperlink_found = True
    if hyperlink_found:
        print("FAIL: ToC/List of Figures/List of Tables entries still carry Hyperlink styling or color 0563C1 — override was documented but not applied. Explicitly set entry run color to 000000 and underline to none.")
        return

    # Expected shape, confirmed across 3 independent real files: 0 empties between ToC and
    # List of Figures; exactly 1 empty after List of Figures' entries before List of Tables.
    #
    # List of Tables -> next section is DIFFERENT and depends on how that next section reaches its
    # own page. The "2 empties" figure the real files show is a byproduct of NATURAL page flow —
    # their own front matter is long enough (multi-page ToC) that Section 1 lands on a fresh page
    # on its own, and those 2 empty paragraphs are just their ordinary spacing convention, not a
    # forced break. A short front matter (single-page ToC, as a smaller enhancement doc's often is)
    # doesn't reach a new page naturally, so generation instead sets `pageBreakBefore: true` on
    # Section 1's own heading to reliably start it on a fresh page regardless of front-matter
    # length. Confirmed via actually rendering a generated file in Word (Word-COM export to PDF,
    # not visible from XML alone): combining that forced break WITH 2 trailing empty paragraphs
    # produces a genuine extra BLANK PAGE between the front matter and Section 1 — some interaction
    # between the TOC field's own SDT boundary, the trailing empty paragraphs, and the forced break
    # that pushes the empties onto their own page before the break fires. Removing the trailing
    # empties entirely (0, not 2) when a forced pageBreakBefore is used eliminates the blank page
    # and Section 1 lands cleanly on the very next page. Use 0 whenever generation forces the next
    # section's page break itself; only use 2 when relying on natural flow with no forced break.
    gap1_empty_count = sum(1 for el in kids[toc_i+1:lof_i] if is_empty(el))
    between_lof_and_lot = kids[lof_i+1:lot_i]
    trailing_empties_lof = 0
    for el in reversed(between_lof_and_lot):
        if is_empty(el): trailing_empties_lof += 1
        else: break
    between_lot_and_next = kids[lot_i+1:next_section_i]
    trailing_empties_lot = 0
    for el in reversed(between_lot_and_next):
        if is_empty(el): trailing_empties_lot += 1
        else: break

    problems = []
    if gap1_empty_count > 0:
        problems.append(f"{gap1_empty_count} empty paragraph(s) between Table of Content and List of Figures (expected 0)")
    if trailing_empties_lof != 1:
        problems.append(f"{trailing_empties_lof} empty paragraphs after List of Figures entries (expected exactly 1)")
    # 0 is correct when the next section forces its own page (pageBreakBefore on that heading —
    # check its own XML directly rather than assuming); 2 is correct only for natural flow with no
    # forced break. Both are valid depending on which mechanism generation used; only flag a value
    # that's neither.
    if trailing_empties_lot not in (0, 2):
        problems.append(f"{trailing_empties_lot} empty paragraphs after List of Tables entries (expected 0 if the next section forces pageBreakBefore, or 2 for natural flow with no forced break — never anything else)")

    if problems:
        print("FAIL: front-matter spacing doesn't match the confirmed shape — " + "; ".join(problems))
    else:
        print("PASS: Table of Contents / List of Figures / List of Tables are real fields with the confirmed spacing shape (0 / 1 / 0-or-2 empty paragraphs).")

def check_body_spacing(docx_path):
    with zipfile.ZipFile(docx_path) as z:
        xml = z.read('word/document.xml').decode('utf-8')
    body = xml[xml.find('<w:body>'):]
    # Top-level paragraphs only (not inside tables — a run of empty cells is not this defect;
    # this checks stacked empty paragraphs in the document flow, e.g. between two sections).
    # Strip table contents first so we only scan paragraphs that sit directly in the body flow.
    # Also strip <w:sdt> blocks (e.g. a real TOC/LoF/LoT field) the same way — same class of bug
    # check_front_matter was already fixed for: a flat regex paragraph split doesn't respect the
    # sdt boundary, so a field's own internal empty paragraphs (fldChar begin/separate/end, no
    # visible text) get miscounted as stacked-empty spacing defects in the surrounding body flow,
    # when they're actually opaque field-internal structure with nothing to do with this check.
    body_no_tables = re.sub(r'<w:tbl>.*?</w:tbl>', '', body, flags=re.S)
    body_no_tables = re.sub(r'<w:sdt>.*?</w:sdt>', '<w:p><w:r><w:t>[field]</w:t></w:r></w:p>', body_no_tables, flags=re.S)
    paras = re.findall(r'<w:p\b.*?</w:p>', body_no_tables, re.S)

    # Cover page and front matter (ToC/LoF/LoT) are exempt — confirmed real-file structure uses
    # stacked empty paragraphs as a vertical-layout mechanism there (see the cover-page exception
    # documented above), which is a different mechanism from body-flow section-transition spacing.
    # Section 1 is the first paragraph carrying <w:numPr> (the first numbered heading) — everything
    # before that index is cover page / front matter and is out of scope for this check.
    section1_idx = next((i for i, p in enumerate(paras) if '<w:numPr' in p), 0)
    paras = paras[section1_idx:]

    def is_empty(p): return '<w:t' not in p and '<w:drawing' not in p

    runs = []
    current_run = 0
    run_start_idx = 0
    for i, p in enumerate(paras):
        if is_empty(p):
            if current_run == 0:
                run_start_idx = i
            current_run += 1
        else:
            if current_run >= 2:
                runs.append((run_start_idx, current_run))
            current_run = 0
    if current_run >= 2:
        runs.append((run_start_idx, current_run))

    if runs:
        print(f"FAIL: {len(runs)} location(s) with 2+ stacked empty paragraphs in the body flow (the standard, checked precisely by check_section_transitions below, is 0 or 1 depending on context — never 2+):")
        for idx, count in runs:
            # print a little context: nearest preceding non-empty paragraph's text, if any
            context = ""
            for j in range(idx - 1, max(idx - 5, -1), -1):
                if not is_empty(paras[j]):
                    ctx = re.search(r'<w:t[^>]*>([^<]*)</w:t>', paras[j])
                    context = (ctx.group(1)[:40] if ctx else "")
                    break
            print(f"  - {count} empty paragraphs, shortly after: {context!r}")
    else:
        print("PASS: no stacked (2+) empty paragraphs found anywhere in the body flow.")

def check_section_transitions(docx_path):
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        xml_bytes = z.read('word/document.xml')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    root = ET.fromstring(xml_bytes)
    kids = list(root.find(f'{Wns}body'))

    def para_style(el):
        s = el.find(f'{Wns}pPr/{Wns}pStyle')
        return s.get(f'{Wns}val') if s is not None else None
    def is_heading(el):
        return el.tag == f'{Wns}p' and para_style(el) in ('Heading1', 'Heading2', 'Heading3') \
            and el.find(f'.//{Wns}t') is not None
    def is_empty_p(el):
        return el.tag == f'{Wns}p' and el.find(f'.//{Wns}t') is None and el.find(f'.//{Wns}drawing') is None

    # The front-matter zone (Table of Contents / List of Figures / List of Tables) has its own
    # more specific spacing shape (0/1/2, not this check's generic 0-or-1 rule) — that's what
    # check_front_matter() validates. Without excluding it here, this generic check re-evaluates
    # the same headings against the wrong rule and false-fails "List of Tables" (real count 1,
    # this check's generic rule wants 0 since nothing there looks like a table/bullet-list) and
    # the first real section heading after it (real count 2, same generic-rule mismatch) even
    # when check_front_matter has already confirmed both counts are exactly correct. Skip both.
    FRONT_MATTER_LABELS = {'Table of Contents', 'Table of Content', 'List of Figures', 'List of Tables'}
    skip_indices = set()
    for i, el in enumerate(kids):
        if is_heading(el) and ''.join(el.itertext()).strip() in FRONT_MATTER_LABELS:
            skip_indices.add(i)
            if ''.join(el.itertext()).strip() == 'List of Tables':
                # also skip the next real heading — Section 1's opening heading, whose leading
                # empty-paragraph count (2, confirmed) belongs to the front-matter shape too.
                for j in range(i + 1, len(kids)):
                    if is_heading(kids[j]):
                        skip_indices.add(j)
                        break

    problems = []
    for i, el in enumerate(kids):
        if not is_heading(el) or i == 0 or i in skip_indices:
            continue
        j = i - 1
        empty_count = 0
        while j >= 0 and is_empty_p(kids[j]):
            empty_count += 1
            j -= 1
        if j < 0:
            continue
        prev = kids[j]
        prev_is_table = prev.tag == f'{Wns}tbl'
        prev_is_list = prev.tag == f'{Wns}p' and para_style(prev) == 'ListParagraph'
        heading_text = ''.join(el.itertext())[:40]
        if prev_is_table or prev_is_list:
            if empty_count != 1:
                kind = "a table" if prev_is_table else "a bullet list"
                problems.append(f'"{heading_text}": preceded by {kind} with {empty_count} empty paragraph(s) (standard is exactly 1)')
        else:
            if empty_count > 0:
                problems.append(f'"{heading_text}": {empty_count} empty paragraph(s) before it, but it does not follow a table/list (standard is 0)')

    if problems:
        print("FAIL: section-transition spacing doesn't match the standard —")
        for p in problems:
            print("  - " + p)
    else:
        print("PASS: every heading after a table/bullet-list has exactly 1 empty paragraph before it; every other heading has 0.")

def check_fonts(docx_path):
    # This is the check that was missing and is the most likely explanation for a user report
    # of "generated fonts/sizes don't match the reference doc" despite the font spec being
    # documented correctly: the FORMATTING CHECKLIST's "Font check" item was eyeball-only, same
    # gap already fixed for numbering — an agent could mark it [PASS] without actually verifying
    # against the XML. Every text-bearing run must carry an explicit rFonts ascii="Candara"
    # (or "Arial" specifically for a lone "→" run) — relying on style/theme inheritance is the
    # documented root cause of font drift (see "Why past output drifted" above).
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        xml_bytes = z.read('word/document.xml')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    root = ET.fromstring(xml_bytes)

    bad_runs = []
    total_checked = 0
    for r in root.iter(f'{Wns}r'):
        t = r.find(f'{Wns}t')
        if t is None or not (t.text or '').strip():
            continue
        text = t.text
        total_checked += 1
        rpr = r.find(f'{Wns}rPr')
        rfonts = rpr.find(f'{Wns}rFonts') if rpr is not None else None
        ascii_font = rfonts.get(f'{Wns}ascii') if rfonts is not None else None
        expected = 'Arial' if text.strip() == '→' else 'Candara'
        if ascii_font != expected:
            bad_runs.append((text[:25], ascii_font, f'expected {expected}'))

    if bad_runs:
        print(f"FAIL: {len(bad_runs)}/{total_checked} text runs missing the correct explicit font — e.g. {bad_runs[:8]}")
        print("Every text-bearing run needs an explicit rFonts ascii override; don't rely on style/theme inheritance.")
        return

    # Second pass, added after a gap report: everything above checks document.xml runs, but the
    # NUMBER GLYPH itself (the auto-generated "7.1.2." Word renders in front of a numbered
    # paragraph) is not a run in document.xml at all — it's synthesized from the list level's own
    # <w:lvl><w:rPr><w:rFonts> in numbering.xml, a third font source separate from both paragraph
    # style and run rPr. A document can pass 100% of the check above while every numbered
    # heading's digits still render in theme Calibri, because nothing was reading numbering.xml.
    # Confirmed for real: even the V1.0 reference file has this exact gap at ilvl=0 of its main
    # heading list (no rFonts override, just <w:rFonts w:hint="default"/>) while ilvl=2 of the
    # same list does have explicit Candara — inconsistent even in the signed-off sample. Target
    # for generated output: every level actually used in the document must have it, no exceptions.
    with zipfile.ZipFile(docx_path) as z:
        if 'word/numbering.xml' not in z.namelist():
            print("PASS: all text-bearing runs correct (no numbering.xml part to check further).")
            return
        num_bytes = z.read('word/numbering.xml')
    num_root = ET.fromstring(num_bytes)

    numid_to_abs = {}
    for n in num_root.findall(f'{Wns}num'):
        ref = n.find(f'{Wns}abstractNumId')
        if ref is not None:
            numid_to_abs[n.get(f'{Wns}numId')] = ref.get(f'{Wns}val')

    used_combos = set()
    for npr in root.iter(f'{Wns}numPr'):
        numid_el = npr.find(f'{Wns}numId')
        if numid_el is None:
            continue
        ilvl_el = npr.find(f'{Wns}ilvl')
        used_combos.add((numid_el.get(f'{Wns}val'), ilvl_el.get(f'{Wns}val') if ilvl_el is not None else '0'))

    level_info = {}
    for absnum in num_root.findall(f'{Wns}abstractNum'):
        absid = absnum.get(f'{Wns}abstractNumId')
        for lvl in absnum.findall(f'{Wns}lvl'):
            rpr = lvl.find(f'{Wns}rPr')
            rfonts = rpr.find(f'{Wns}rFonts') if rpr is not None else None
            ascii_font = rfonts.get(f'{Wns}ascii') if rfonts is not None else None
            numfmt_el = lvl.find(f'{Wns}numFmt')
            numfmt = numfmt_el.get(f'{Wns}val') if numfmt_el is not None else None
            level_info[(absid, lvl.get(f'{Wns}ilvl'))] = (ascii_font, numfmt)

    # Bullet levels (Assumptions/Risks/Scope/Test Scenarios) legitimately render their glyph via
    # a symbol font (e.g. "Symbol"), not Candara — only decimal-numbered levels need Candara.
    bad_levels = []
    for numid, ilvl in used_combos:
        absid = numid_to_abs.get(numid)
        if absid is None:
            continue
        ascii_font, numfmt = level_info.get((absid, ilvl), (None, None))
        if numfmt == 'bullet':
            continue
        if ascii_font != 'Candara':
            bad_levels.append((numid, ilvl, ascii_font))

    if bad_levels:
        print(f"FAIL: {len(bad_levels)} used (numId, ilvl) list level(s) missing explicit Candara in numbering.xml's <w:lvl><w:rPr><w:rFonts> — the number glyph itself will render in the theme font regardless of run-level correctness. (numId, ilvl, found_font): {bad_levels[:8]}")
        print("Fix in numbering.xml, not document.xml: add rFonts ascii=\"Candara\" hAnsi=\"Candara\" to each affected <w:lvl>'s <w:rPr>.")
    else:
        print(f"PASS: all {total_checked} text-bearing runs and all {len(used_combos)} used list levels carry explicit Candara.")

def check_colors(docx_path):
    # Same rationale as check_fonts(): the "Color check" checklist item was eyeball-only.
    # Scoped to the two highest-visibility, most-reported elements — cover title and section
    # headings — not every color rule in this document (nav paths, captions, etc. are not yet
    # covered here; still verify those by eye per the FORMATTING CHECKLIST until this is extended).
    #
    # Two design bugs fixed after testing against real files:
    # 1. "First Heading1-styled paragraph = cover title" is wrong — one real file styles its
    #    cover title as plain "Normal", not "Heading1", so that heuristic landed on "Table of
    #    Contents" instead and wrongly demanded 0070C0 on it. Cover title is now identified by
    #    document position (the first non-empty paragraph, any style), not by style.
    # 2. Unlike fonts, heading COLOR can legitimately come from the Heading1/Heading2 paragraph
    #    STYLE itself (confirmed: real files bake color=2F5496 into the style definition, so
    #    individual headings don't need a per-run override to render correctly) — this is a
    #    different, safe case from fonts (where the style only provides the theme's Calibri, so
    #    per-run Candara really is required). A heading with no run-level color override is only
    #    a defect if the style itself ALSO doesn't provide 2F5496.
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        xml_bytes = z.read('word/document.xml')
        styles_bytes = z.read('word/styles.xml')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    root = ET.fromstring(xml_bytes)
    styles_root = ET.fromstring(styles_bytes)
    kids = list(root.find(f'{Wns}body'))

    def para_style(el):
        s = el.find(f'{Wns}pPr/{Wns}pStyle')
        return s.get(f'{Wns}val') if s is not None else None
    def run_colors(el):
        return {c.get(f'{Wns}val') for c in el.findall(f'.//{Wns}color')}
    def style_default_color(style_id):
        for s in styles_root.iter(f'{Wns}style'):
            if s.get(f'{Wns}styleId') == style_id:
                c = s.find(f'{Wns}rPr/{Wns}color')
                return c.get(f'{Wns}val') if c is not None else None
        return None

    FRONT_MATTER_LABELS = {'Table of Contents', 'Table of Content', 'List of Figures', 'List of Tables'}
    problems = []

    # Cover title: first non-empty paragraph, any style, checked by position not style.
    cover_title_el = next((el for el in kids if el.tag == f'{Wns}p' and ''.join(el.itertext()).strip()), None)
    if cover_title_el is not None and '0070C0' not in run_colors(cover_title_el):
        text = ''.join(cover_title_el.itertext()).strip()
        problems.append(f'Cover title {text[:40]!r}: expected color 0070C0 somewhere in its runs, found {run_colors(cover_title_el) or "none (no explicit color at all)"}')

    # Numbered section headings: run-level 2F5496 OR the paragraph style's own default is 2F5496.
    for el in kids:
        if el.tag != f'{Wns}p' or para_style(el) not in ('Heading1', 'Heading2') or el is cover_title_el:
            continue
        text = ''.join(el.itertext()).strip()
        if not text or text in FRONT_MATTER_LABELS:
            continue
        has_numpr = el.find(f'{Wns}pPr/{Wns}numPr') is not None
        if not has_numpr:
            continue
        colors = run_colors(el)
        style_color = style_default_color(para_style(el))
        if '2F5496' not in colors and style_color != '2F5496':
            problems.append(f'Heading {text[:40]!r}: expected color 2F5496 (run-level or via its "{para_style(el)}" style default), found run colors {colors or "none"} and style default {style_color!r}')

    if problems:
        print(f"FAIL: {len(problems)} heading(s) with wrong/missing color —")
        for p in problems:
            print("  - " + p)
    else:
        print("PASS: cover title uses 0070C0 and all numbered section headings use 2F5496.")

def check_table_styles(docx_path):
    # Added after a real defect: several tables (Document Information, Definitions & Acronyms,
    # General Guide Line, story tables, Epic table) were generated with manual tblBorders only and
    # NO tblStyle reference at all. Borders still rendered correctly, so this looked fine in every
    # prior XML check — but it silently loses the named style's own default cell margins, which is
    # what actually produces the visible padding real files have around numbered content inside
    # table cells (confirmed only by a user-provided screenshot comparison, not by any check that
    # existed before this one). Every table in this document format must reference a named style
    # (GridTable4-Accent3, PlainTable1, or TableGrid — see Table styles above); manual borders alone
    # are not equivalent and this check exists specifically so that gap doesn't require a human
    # screenshot to catch a second time.
    import xml.etree.ElementTree as ET
    with zipfile.ZipFile(docx_path) as z:
        xml_bytes = z.read('word/document.xml')
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    root = ET.fromstring(xml_bytes)

    def find_tables(el):
        for child in el:
            if child.tag == f'{Wns}tbl':
                yield child
            for tc in child.iter(f'{Wns}tc'):
                yield from find_tables(tc)

    problems = []
    tables = list(root.find(f'{Wns}body').iter(f'{Wns}tbl'))
    for i, tbl in enumerate(tables):
        tblPr = tbl.find(f'{Wns}tblPr')
        style = tblPr.find(f'{Wns}tblStyle') if tblPr is not None else None
        if style is None or not style.get(f'{Wns}val'):
            # identify the table by its first cell's text for a useful error message
            first_text = ''
            p = tbl.find(f'.//{Wns}p')
            if p is not None:
                first_text = ''.join(p.itertext()).strip()[:40]
            problems.append(f'Table #{i+1} (starts "{first_text}") has no tblStyle reference')

    if problems:
        print(f"FAIL: {len(problems)} table(s) with no named tblStyle —")
        for p in problems:
            print("  - " + p)
        print("  Every table must set style: \"GridTable4-Accent3\" / \"PlainTable1\" / \"TableGrid\" — manual borders alone are not equivalent (see Table styles section).")
    else:
        print(f"PASS: all {len(tables)} table(s) reference a named tblStyle.")

def check_no_cell_margins(docx_path):
    # Added after a real defect: a `margins` override on table-cell helpers (confirmed nowhere in
    # any real file — see the Spacing section's "Cell margins: none" entry) combined with another
    # mistake to inflate single-line table row height ~2.4x versus real files. Mechanical, so this
    # doesn't require re-rendering and re-measuring in Word to catch a recurrence.
    with zipfile.ZipFile(docx_path) as z:

    if count:

    else:
        print("PASS: no table cell has an explicit tcMar override.")

def check_heading_indent_progression(docx_path):
    # Added after a real defect: a numbering config with `hanging == left` at every level makes
    # every heading level's number GLYPH start at the same position (0) regardless of level — "1."
    # and "1.1." both flush left, only the tab-to-text distance differs. Only caught previously by
    # a user screenshot comparing against a real file; this check makes it mechanical. Real files'
    # own values: number-start (left-hanging) must strictly increase from level 0 to level 1 for
    # any numbering list used on Heading1/Heading2 paragraphs.
    import xml.etree.ElementTree as ET
    Wns = '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}'
    with zipfile.ZipFile(docx_path) as z:
        doc_bytes = z.read('word/document.xml')
        num_bytes = z.read('word/numbering.xml')
    root = ET.fromstring(doc_bytes)
    num_root = ET.fromstring(num_bytes)

    def para_style(el):
        s = el.find(f'{Wns}pPr/{Wns}pStyle')
        return s.get(f'{Wns}val') if s is not None else None
    def numid_of(el):
        n = el.find(f'{Wns}pPr/{Wns}numPr/{Wns}numId')
        return n.get(f'{Wns}val') if n is not None else None

    numid_to_abs = {}
    for n in num_root.findall(f'{Wns}num'):
        ref = n.find(f'{Wns}abstractNumId')
        if ref is not None:
            numid_to_abs[n.get(f'{Wns}numId')] = ref.get(f'{Wns}val')

    # Collect every distinct numId actually used on a Heading1 or Heading2 paragraph.
    heading_numids = set()
    for el in root.iter(f'{Wns}p'):
        if para_style(el) in ('Heading1', 'Heading2'):
            nid = numid_of(el)
            if nid:
                heading_numids.add(nid)

    def level_start(absid, ilvl):
        for absnum in num_root.findall(f'{Wns}abstractNum'):
            if absnum.get(f'{Wns}abstractNumId') == absid:
                lvl = absnum.find(f'{Wns}lvl[@{Wns}ilvl="{ilvl}"]')
                if lvl is None:
                    return None
                ind = lvl.find(f'{Wns}pPr/{Wns}ind')
                if ind is None:
                    return None
                left = int(ind.get(f'{Wns}left', 0))
                hanging = int(ind.get(f'{Wns}hanging', 0))
                return left - hanging
        return None

    problems = []
    for numid in heading_numids:
        absid = numid_to_abs.get(numid)
        if absid is None:
            continue
        start0 = level_start(absid, 0)
        start1 = level_start(absid, 1)
        if start0 is None or start1 is None:
            continue
        if start1 <= start0:
            problems.append(f'numId {numid}: level-0 number starts at {start0}, level-1 at {start1} — level 1 must start further right than level 0 (heading numbers need progressive indent, not left==hanging at every level)')

    if problems:
        print(f"FAIL: {len(problems)} heading numbering list(s) don't indent progressively —")
        for p in problems:
            print("  - " + p)
    else:
        print(f"PASS: all {len(heading_numids)} heading numbering list(s) indent level 1 further right than level 0.")

def check_no_docdefault_paragraph_spacing(docx_path):
    # Added after a confirmed real regression: setting styles.default.document.paragraph.spacing
    # (docx-js) — i.e. <w:docDefaults><w:pPrDefault><w:pPr><w:spacing .../></w:pPr></w:pPrDefault> —
    # cascades into every table cell paragraph that doesn't reference a named style with its own
    # protective pPr (Document Information, Definitions & Acronyms, General Guide Line, story
    # tables, Epic table, the cover table), inflating single-line row height ~1.5-2.4x versus real
    # files (measured: real ~14.0pt gap between single-line rows; the regressed version produced
    # ~22-34pt). This was set once specifically to fix a cover-page blank-spacer gap and broke every
    # table's row height as a side effect — confirmed by actual Word rendering with pixel-position
    # measurement, invisible to every other structural check. No real reference file sets a non-zero
    # spacing in pPrDefault; whatever spacing individual elements need (e.g. blank() spacer
    # paragraphs) must be set on that specific paragraph, never at the document-default level.
    import re
    with zipfile.ZipFile(docx_path) as z:
        styles = z.read('word/styles.xml').decode('utf-8')
    m = re.search(r'<w:pPrDefault>(.*?)</w:pPrDefault>', styles, re.S)
    if m and re.search(r'<w:spacing\b', m.group(1)):
        print(f"FAIL: styles.xml sets a document-level default paragraph spacing (w:docDefaults/w:pPrDefault) — {m.group(1)[:200]!r}. This cascades into every table cell without its own protective style and inflates row height. Move any needed spacing onto the specific paragraph that needs it (e.g. blank()); leave pPrDefault empty.")
    else:
        print("PASS: no document-level default paragraph spacing set in styles.xml (w:pPrDefault is empty or absent).")

def check_toc_field_live(docx_path):
    # Verifies the ToC/LoF/LoT fields are in the specific "live but resolved" state this skill
    # requires (see docx-formatting.md's "Table of Content / List of Figures / List of Tables must
    # be genuine, live, updatable Word fields" section) — not the empty/dirty state (broken, shows
    # blank until manually updated) and not stripped-to-static-text (loses the ability to
    # right-click > Update Field after future edits, explicitly rejected by the user once already).
    # Three checks: (1) no <w:sdt> content-control wrapper anywhere (docx-js adds one; a native Word
    # TOC field never has one — its presence is itself evidence the field wasn't fully processed);
    # (2) no w:dirty="true" anywhere (correct only while the cache is still empty/placeholder; must
    # be cleared once real content is filled in — its presence means either the fix wasn't applied
    # at all, or was applied to a still-empty cache); (3) every fldChar begin has a matching end (an
    # unbalanced count means a field boundary got corrupted, e.g. by a botched sdt-strip or
    # boundary-merge). Does NOT check that page numbers are real (see check_toc_page_numbers_real
    # below for that, since it also depends on Word actually having been run against the file).
    import re
    with zipfile.ZipFile(docx_path) as z:
        doc = z.read('word/document.xml').decode('utf-8')
    problems = []
    if '<w:sdt>' in doc:
        problems.append(f"{doc.count('<w:sdt>')} <w:sdt> content-control wrapper(s) still present — docx-js's TableOfContents() wraps ToC/LoF/LoT in one; a native Word TOC field never has one. Strip it (see postprocess.py / postprocess_template.py).")
    if 'w:dirty="true"' in doc:
        problems.append(f"{doc.count('w:dirty=\"true\"')} w:dirty=\"true\" attribute(s) still present — only correct while the field's cache is genuinely empty; must be cleared once real entries/page numbers are filled in.")
    begin_n = doc.count('fldCharType="begin"')
    end_n = doc.count('fldCharType="end"')
    if begin_n != end_n:
        problems.append(f"fldChar begin count ({begin_n}) != end count ({end_n}) — a field boundary is corrupted or orphaned.")
    if problems:
        print("FAIL: ToC/LoF/LoT field(s) not in the required live-and-resolved state —")
        for p in problems:
            print("  - " + p)
    else:
        print(f"PASS: ToC/LoF/LoT fields are live (no w:sdt wrapper, no stale w:dirty flag, {begin_n} balanced field boundaries).")

def check_toc_page_numbers_real(docx_path):
    # Real pagination cannot be computed by this generation pipeline at all (no layout engine) — the
    # cache is filled with placeholder "1" for every entry until a required second phase
    # (get_page_numbers.ps1 + patch_page_numbers.py, via a read-only Word-COM pass) patches in real
    # values. This check catches the case where that second phase was skipped or forgotten before
    # presenting the file — heuristic: every ToC/LoF/LoT entry showing the exact same page number
    # (especially "1") across a document with more than a handful of entries is overwhelmingly
    # unlikely to be genuine pagination. Not a strict "no entry may be literally 1" rule, since a
    # very short document's first entry can legitimately land on page 1 — the signal is uniformity
    # across ALL entries, not any single value.
    import re
    with zipfile.ZipFile(docx_path) as z:
        doc = z.read('word/document.xml').decode('utf-8')
    pat = re.compile(
        r'<w:hyperlink w:anchor="_Toc\d+"[^>]*>.*?fldCharType="separate"/></w:r><w:r><w:rPr>.*?</w:rPr><w:t>([^<]*)</w:t>',
        re.S,
    )
    values = pat.findall(doc)
    if len(values) < 2:
        print(f"FAIL: found only {len(values)} ToC/LoF/LoT page-number entries — expected several; inspect manually.")
    elif len(set(values)) == 1:
        print(f"FAIL: all {len(values)} ToC/LoF/LoT entries show the identical page number ({values[0]!r}) — almost certainly still the unpatched placeholder. Run get_page_numbers.ps1 + patch_page_numbers.py before presenting.")
    else:
        print(f"PASS: {len(values)} ToC/LoF/LoT entries show {len(set(values))} distinct real page numbers (not a uniform placeholder).")

def check_hex_ids(docx_path):
    # Added after a confirmed hard-open failure while hand-splicing new paragraphs/images directly
    # into an existing real .docx via raw XML edits (not docx-js generation): w14:paraId (on w:p)
    # and wp14:anchorId/wp14:editId (on wp:inline/wp:anchor) are all typed ST_LongHexNumber in the
    # OOXML schema — exactly 8 hex digits, ^[0-9A-Fa-f]{8}$. An "invented" value containing a
    # non-hex letter (e.g. "6A1K0001", "6A1L0004" — K and L are not hex digits) is schema-invalid
    # and Word refuses to open the file at all ("Word experienced an error trying to open the
    # file... Try the Text Recovery converter") — same hard-open failure class as rId0 and the
    # missing wrapPolygon documented above, a new root cause. Confirmed via a minimal reproduction
    # ladder: a relationships+media-only change with no document.xml edit opened fine; one single
    # new image paragraph with an invalid-hex paraId reproduced the failure in isolation; switching
    # that same paraId to valid hex (e.g. "6A1C0001") fixed it immediately, nothing else changed.
    import re
    with zipfile.ZipFile(docx_path) as z:
        doc = z.read('word/document.xml').decode('utf-8')
    HEX8 = re.compile(r'^[0-9A-Fa-f]{8}$')
    bad = []
    for attr in ('w14:paraId', 'wp14:anchorId', 'wp14:editId'):
        for m in re.finditer(attr + r'="([^"]*)"', doc):
            val = m.group(1)
            if not HEX8.match(val):
                bad.append((attr, val))
    if bad:
        print(f"FAIL: {len(bad)} id attribute(s) are not valid 8-digit hex (ST_LongHexNumber) — Word will hard-refuse to open the file: {bad[:10]}")
        print("Fix: replace each with a value matching ^[0-9A-Fa-f]{8}$ (e.g. 6A1C0001, not 6A1K0001 — K/L/etc. are not hex digits).")
    else:
        print("PASS: every w14:paraId / wp14:anchorId / wp14:editId attribute is valid 8-digit hex.")
```

advisory. Fix the specific paragraphs flagged and re-run the script; don't just re-eyeball the
document and assume it's fixed:
- `check_numbering` → typed 3-5 level decimal numbers (story sub-points like `7.1.2.1.`): convert to real `numbering:{reference, level}` paragraphs.
- `check_numbering_gap` → confirmed on a real generated file: `suff="nothing"` used outside the documented COM-Save exception, or a literal leading space/tab typed into a numbered paragraph's first run. Fix: set `suff="tab"` per the documented recipe, remove any leading space/tab characters from the text.
- `check_heading_numbering` → typed 1-2 level numbers baked into Heading1/2/3 text (`1.`, `1.6.`), or a heading with no `numPr` at all: apply real multilevel heading numbering instead.
- `check_bullets` → typed `•`/`-`/`*` characters instead of real bullet `numPr` on Assumptions/Risks/Scope/Test-Scenario items.
- `check_second_list_start` → Data Dictionary's second numbering list isn't independently restarting at Features/Stories' actual section number (reuses the same list, or restarts at the wrong value): give it its own list with `start` set to match.
- `check_front_matter` → covers four things now: (1) Table of Contents/List of Figures/List of Tables are real fields, not typed text; (2) none of those 3 headings carry `numPr` and Section 1's heading immediately after them does — fix a heading incorrectly numbered as `1.1.` or incorrectly left unnumbered; (3) no Hyperlink-styled or `0563C1`-colored run anywhere in the front matter — a real field defaults to blue/underlined automatically (confirmed in every real sample), so this must be an explicit override to plain, not an absence of one; a `FAIL` here means the override didn't land — set entry run color to `000000`, underline to none; (4) add/remove empty paragraphs until the counts are exactly 0/1/2, confirmed identically across three independent real files.

- `check_table_styles` → a table with no named `tblStyle` (only manual `tblBorders`): add `style: "GridTable4-Accent3"` / `"PlainTable1"` / `"TableGrid"` per the Table styles section — manual borders alone still render correctly but silently lose the style's own default cell margins.
- `check_no_cell_margins` → a table cell with an explicit `tcMar`/`margins` override: remove it. No real file has this anywhere; it was a confirmed real cause of ~2.4x row-height inflation.
- `check_heading_indent_progression` → a heading numbering list where level 1's number doesn't start further right than level 0's (`left - hanging` not increasing): fix the list's `indent` values per level — see the Numbering section's real `left`/`hanging` table. - `check_toc_field_live` → any of: an `<w:sdt>` wrapper still present, a stale `w:dirty="true"` attribute, or an unbalanced `fldChar` begin/end count: see postprocess.py's sdt-strip + dirty-clear + boundary-merge logic (and the corresponding section in this file) — the ToC/LoF/LoT fields must stay genuinely live (updatable via right-click), not stripped to static text, but also not left in the broken empty/dirty state.

- `check_hex_ids` → a `w14:paraId`/`wp14:anchorId`/`wp14:editId` value that isn't exactly 8 hex characters: replace it with real hex (e.g. `%08X` of a random 32-bit value). Confirmed as a hard-open-failure cause when hand-splicing new paragraphs/images into an existing real file — see the dedicated section above.

**None of these seventeen checks can see how the file actually renders — they're all XML-structural.**
Margins, spacing gaps, row height, and page layout are real-Word-rendering properties, not
inspectable from the tree. If Word is available in this environment (check for `WINWORD.EXE`),
render the file via Word COM automation and actually look at it, page by page, against a real
reference file rendered the same way, before presenting — see STEP 2.5 / Pass 2 in SKILL.md for
the exact procedure. Every visual defect fixed on this project (cover-page spacing, table row
height, numbering indent, header/footer mechanism) passed all applicable scripted checks the whole
time it was wrong; it was only ever caught by actually rendering the file or by a user screenshot.

Between them, these seven checks now cover every numbering context in the document: heading
numbers and sub-headings (`check_heading_numbering`), story sub-points inside table cells
(`check_numbering`), bullet lists (`check_bullets`), the Data-Dictionary-onward restart/multilevel
quirk (`check_second_list_start`), and the Table of Contents/List of Figures/List of Tables field
mechanism (`check_front_matter`).

**What the scripts can't check — verify these by reading the generated file directly:** table
cell paragraphs (single vs multi-paragraph spacing overrides), image-to-caption adjacency, and
caption-to-next-figure adjacency aren't reliably detectable by a generic XML regex the way typed
numbers or paragraph counts are — read the "Spacing — full audit" section above and check the
generated document by eye against those specific exact-adjacency rules (0 empty paragraphs at
each of those transitions) as part of Pass 2.

**Red flags — if you catch yourself thinking any of these while generating, stop and use real
list numbering instead:**
- "It's faster to just type the number" — it's also exactly the defect a user already reported.
- "It'll look the same either way" — it looks the same, it doesn't behave the same; that gap is
  invisible until someone edits the document, which is the whole point of a Word deliverable.
- "I'll fix the numbering mechanism later, get the content right first" — the mechanism is not a
  polish pass, it's part of what "correct" means for this element; a typed number is not a draft
  version of a real one, it's a different, wrong thing.
- "This one paragraph is a one-off, not worth setting up a list for" — every numbered paragraph in
  the document is a "one-off" in this sense; the list definition is reused across all of them.

## Verifying a hand-edited existing real .docx — not just this skill's own from-scratch generation

Everything in the MANDATORY section above, and everywhere else this file talks about "generating"
the file, assumes this skill is building a brand-new `.docx` via docx-js/python-docx from a blank
slate. Hand-editing an **existing real `.docx`** directly (splicing in new XML rather than
generating fresh — the same territory as the OLE-embedding and tracked-changes sections above, and
the in-place numbering patch already documented under "Patching an already-generated real .docx in
place is a different, riskier operation than building one fresh") is a different, higher-risk
operation and needs its own explicit minimum verification bar, generalized from that same lesson
rather than re-learned per defect class:

1. `zipfile.testzip()` comes back clean.
2. Every `.xml`/`.rels` part parses via `xml.etree.ElementTree.fromstring` with zero exceptions.
3. `python-docx`'s `Document(path)` opens without raising.
4. Word-COM opens the file with no error/repair dialog — open with `ReadOnly=True` passed to
   `Documents.Open`, close without saving, specifically so a pure verification pass can never
   accidentally trigger the docx-js style-stripping regression documented elsewhere in this file.
5. Whenever a part is claimed to be "untouched," actually verify it, don't assume it from the diff
   you intended to make: SHA-256-compare it against a pre-edit backup copy of the same file **if no
   real Word `Save()` occurred anywhere in the pipeline**. If a real Word `Save()` did occur
   somewhere in the pipeline (e.g. the OLE-embedding recipe above), SHA-256 will legitimately
   differ — Word re-serializes on every save — so compare *parsed content* instead (e.g. for
   comments: parse both versions' `comments.xml` and assert the list of `(id, author, text)` tuples
   is identical, not the raw bytes).

None of these five checks are optional for a hand-edited file just because the change "looks
small" — `check_hex_ids()` above exists precisely because a one-paragraph splice with an
otherwise-perfect diff still hard-failed to open, for a reason invisible to steps 1-3 and only
caught by treating the file as needing the same discipline as a fresh generation.

### A stray Unicode private-use marker can silently break an exact-string match right after an edit tool inserts it

Smaller, but real, and worth knowing before assuming a broken assertion means broken logic. When
using a code-editing tool to insert a short literal marker/placeholder string into a source file
(e.g. a Python or JS string literal used purely as a find-anchor for later regex-based
post-processing), the inserted text was found — on later inspection — to be silently wrapped in a
pair of U+E000 (Private Use Area) characters that were never intentionally typed. This broke an
exact-string-match assertion downstream in a confusing way: the mismatch was invisible when the
file was printed to a terminal or log, since many terminal encodings render or silently swallow
that codepoint, and it only surfaced via a byte-level `repr()`/character-by-character diff.

**Lesson:** when a "this exact string must be found verbatim" assertion fails unexpectedly right
after using an edit tool to place that exact string, don't just re-read the file and eyeball it —
do a `repr()` or byte/codepoint-level diff of the actual file content against the expected constant
before assuming the surrounding logic itself is wrong.
